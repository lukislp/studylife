# StudyLife — Architecture & Developer Documentation

Short technical overview for future changes. Feature description from a user's perspective lives in the [README](../README.md).

## Structure

```
Client (Blazor WASM)  <-- HTTP/JSON -->  Server (ASP.NET Core)  <-- EF Core -->  SQLite
```

- **StudyLife.Client** — Blazor WebAssembly SPA, runs entirely in the browser. Holds local caches in `AppStateService` and polls the server every 30s. [StudyLife.App](https://github.com/lukislp/studylife-app) (a separate repo, .NET MAUI Blazor Hybrid) pulls this project in via a plain project reference — no copy — so the native iOS/Android/Windows/macOS shell and the browser/PWA client always render the identical UI.
- **StudyLife.Server** — ASP.NET Core Minimal Hosting (`Program.cs`), serves the WASM files and exposes the REST API. **Web Push reminders/weekly reports/APNs Live Activity updates do NOT run inside this same role** — they're `BackgroundTaskService`'s 30s tick loop, gated behind `Worker:Enabled` (see [Background services](#background-services-server) below). A single-container deployment (`docker run`/`dotnet run`, `Worker:Enabled` defaulting to `true`) runs both roles combined in one process; production and the horizontally-scalable setup (Kubernetes/K3s, `docker-compose.scale.yml` for local testing of the same split, see [SCALING.md](SCALING.md)) run them as **separately scaled replicas of the same image** instead (`server`: `Worker:Enabled=false`, web traffic only; `worker`: `Worker:Enabled=true`, exactly one shard set) specifically so that N web replicas never fire the same push reminder N times.
- **StudyLife.Shared** — DTOs referenced by both client and server (`Dtos.cs`, `PushSubscriptionDto.cs`, `CourseCatalog.cs`). Any change to a DTO automatically affects both sides.

Since the multi-user overhaul (phases 1–3, see the dedicated sections below), there are **real user accounts with passkey/WebAuthn login**: the browser client authenticates exclusively via its passkey session (`X-Session-Token`), while Home Assistant and similar non-interactive integrations use a **long-lived per-user API key** (`X-Api-Key`, generated via the Setup page, see [Security](#security) below). The former global, monthly-rotating shared-secret key along with its bootstrap endpoint no longer exists.

## Data model

| Entity (`Data/StudyLifeDb.cs`) | Purpose |
|---|---|
| `StudySessionEntity` | A planned/held study unit (course, time range, topic, notes, timer mode, completed flag) |
| `UserSettingsEntity` | Singleton row (always only one record) with selected courses, theme, motivation style, etc. `SelectedCourseIds`/`CompletedCourseIds` are **comma-separated strings**, not real list columns |
| `PushSubscriptionEntity` | Web Push endpoints for the browser notification system |
| `SentReminderEntity` | Prevents duplicate push reminders after a server restart (key format `"{sessionId}:reminder{minutes}"`) |
| `NoteEntity` | Free-text notes, optionally tied to a course and/or a session — both `CourseId`/`SessionId` are validated at write time when set (`CourseResolver` / a session-existence check), see the API table below |
| `CourseGoalEntity` | Study goal per course: optional `TargetDate` + `CompletionNote`/`CompletedAt`/`Grade` (decimal, German grading scale 1.0–5.0, validated server-side). `CourseId` is unique (one record per course), upserted via `PUT /api/coursegoals/{courseId}`. As with sessions, `CourseName` is stored duplicated, since the course id is not bound to the catalog by a DB foreign key (the catalog lives in `StudyLife.Shared`, not in the DB, see below) — but it is validated at write time (audit finding M2, `CourseResolver`), see the API table below |
| `TimerStateEntity` | One row per user (`AuthUserId`), holding the last focus-timer state reported by that user's client (`SessionId`, `IsRunning`, `IsBreak`, `CurrentRound`, `TimerModeId`, `PhaseEndsAt`). Only pushed on state transitions (start/pause/phase change/completion), not every second — see TimerService below |

**The course catalog lives in `StudyLife.Shared`, not in the DB.** The list of all courses (name, code, icon, color, topics, `Ects` points per semester) is static code in [`StudyLife.Shared/CourseCatalog.cs`](../src/StudyLife.Shared/CourseCatalog.cs) (`CourseCatalog.AppliedAICourses`, type `CourseDto`) and is served via `GET /api/courses` (`CoursesController`, no DB access — a pure in-memory constant). Client and server reference the same assembly, so there is now only **one** source for the catalog. `StudySessionDto`/`CourseGoalDto` still freeze `CourseName`/`CourseColor` at creation time on the respective row (as before) — that doesn't change, since sessions/goals should keep their historical name even after a future catalog change. Anyone changing the study program/course list now does so exclusively in `CourseCatalog.cs`. The `Ects` values (default 5, projects 10, semester 5/6 modules 15 — totaling 180 across all 6 semesters) are **placeholders** for a fictional example curriculum and should be adjusted for the real program; they feed into the weighted grade average and the ECTS progress (see the evaluation page).

**CourseId validation on writes (audit finding M2).** Every write path that binds a row to a course (`POST`/`PUT /api/sessions`, `PUT /api/coursegoals/{courseId}`, `POST /api/sessiontemplates`, `POST /api/courseresources`, `POST`/`PUT /api/notes` when `CourseId` is non-null) now resolves the caller's `CourseId` via `CourseResolver` (`Services/CourseResolver.cs`) against the calling user's FULL course universe: the built-in catalog above, plus ALL of that user's custom courses across EVERY study program they own — not just the currently active one, since a session/goal can legitimately reference a course from a program that was active when the id was first obtained via `GET /api/courses` (this also covers Home Assistant, whose cached course list can predate a later program switch). An unresolvable `CourseId` is rejected with `400 BadRequest` and a stable message naming the id (`CourseId {id} does not exist.`). On a successful write, `CourseName`/`CourseColor` are DERIVED from the resolved course — client-supplied values for these two fields are silently ignored (the DTO fields remain for wire compatibility, but are effectively output-only on these paths now; `NoteDto` has no name/color fields to derive, only the id itself is validated). Frozen-at-creation semantics are preserved rather than replaced: a `PUT` that leaves a row's `CourseId` UNCHANGED is never re-validated and never re-derives the name/color, even if the referenced custom course has since been deleted — this is what keeps editing/completing a session, goal, or note of a deleted course working (e.g. via the focus timer) and keeps a goal's historical name from silently changing on a later, unrelated edit. Only an ACTUALLY CHANGED `CourseId` goes through resolution (and, on success, re-freezes a fresh name/color where applicable). `BackupController`'s raw `.db` restore and the `POST /api/backup/import-json` full-replace path intentionally bypass this validation entirely (see that controller's own doc comments) — they carry historical ids by design and write directly via EF, not through the controllers described here. `BackgroundTaskService.CaptureEnrichment`'s note-course match (see below) resolves the same way but degrades instead of rejecting: an unresolvable `CourseId` from studylife-ai is stored as `null` with a logged warning, since a background job has no caller to hand a `400` back to.

**SessionId validation on writes.** `POST`/`PUT /api/notes` additionally validates a non-null `SessionId` the same way — must resolve to an existing session (implicitly scoped to the calling user via `StudyLifeDb`'s global query filter), `400` with a stable message (`SessionId {id} does not exist.`) otherwise, same frozen/unchanged-on-PUT exemption as `CourseId` above. `PUT /api/timerstate` deliberately does NOT reject a dangling `SessionId` the same way — see its own row below — because it's a high-frequency, fire-and-forget sync path with no caller left to retry a rejected write.

## Single-Timezone Invariant

Every persisted time that represents "when something happens for the user" — `StudySessionEntity.StartTime`/`EndTime`, `TimerStateEntity.PhaseEndsAt`, the reminder/streak/week-boundary calculations derived from them — is a **naive local timestamp** (no UTC, no offset), not a genuinely timezone-aware one. This works today because there is exactly ONE timezone in play end to end:

- The container pins the OS timezone via `ENV TZ=Europe/Berlin` (`src/StudyLife.Server/Dockerfile`), so `DateTime.Now` on the server means the same wall-clock time a user in that timezone would read off a clock.
- The Blazor client (browser or the MAUI shell) reads/writes the same naive values and pushes its OWN local time back for anything time-sensitive — e.g. `TimerStateEntity.PhaseEndsAt` is sent by `TimerService.cs` as the client's local wall-clock time (`ToLocalTime()` on its internally-tracked instant), not something the server computes independently — so both sides agree only because both sides run in the same timezone.
- Any code comparing a boundary against one of these columns (history windows, the ICS export range, streak/week cutoffs) must use `DateTime.Now`, never `DateTime.UtcNow` — mixing the two silently shifts the boundary by the host's UTC offset (audit finding Z1; see `SessionsController.GetHistory`/`GetIcs`). Genuinely UTC-based values — session/auth tokens, `CreatedAt`/`ExpiresAt` audit columns, anything with no relation to a specific user's wall clock — are unaffected and correctly stay on `DateTime.UtcNow`.
- `SessionsController.GetAll()` returns the user's full session history unbounded (no date window at all, since the client does its own week/day navigation over the complete set) — the -7d/+90d window described below applies only to the ICS feed (`GetIcs`), not to `GetAll`.

**What a real multi-timezone future would require** (not planned, but the shape of the change if it ever is): store all of these columns as genuine UTC instants instead of naive local values, add a per-user timezone setting (there is currently nowhere to even record one — the app has exactly one implicit timezone, the server's), and convert at every edge that currently assumes "local" today — the ICS export, push/reminder scheduling, streak/week-boundary math, and the client's own `PhaseEndsAt` computation. Until then, treat any StudyLife time value (in the DB, in the API, in an ICS export) as if it came from the same timezone as the server host — never parse it as UTC.

## API (`Controllers/`)

All routes live under `/api`, return/expect JSON, and require a passkey session token (`X-Session-Token`) or a per-user API key (`X-Api-Key`) — see [Security](#security) — except the handful of endpoints explicitly marked `[AllowAnonymous]` (login/registration, the public progress-share link, `/api/system/version`).

| Route | Method | DTO | Note |
|---|---|---|---|
| `/api/sessions` | GET | `StudySessionDto[]` | No date window — returns the user's full session history; the client does its own week/day navigation over the complete set |
| `/api/sessions` | POST | `StudySessionDto` → `StudySessionDto` | `Id` is ignored/overwritten. Validated: `CourseId > 0`, `CourseName` not empty, `EndTime > StartTime` (otherwise `400 BadRequest`); `CourseId` must additionally resolve against the user's full course universe (`400` with a stable message otherwise, see "CourseId validation on writes" above) — `CourseName`/`CourseColor` are then derived from the resolved course, client-supplied values are ignored |
| `/api/sessions/{id}` | PUT | `StudySessionDto` | 404 if unknown; same field validation as POST. `CourseId` is only re-resolved (and `CourseName`/`CourseColor` re-derived) if it actually CHANGED from the stored row — an unchanged `CourseId` is never rejected and keeps its frozen name/color, even for a since-deleted custom course |
| `/api/sessions/{id}` | DELETE | – | 404 if unknown |
| `/api/sessions/ics` | GET | `text/calendar` | Hand-rolled iCalendar feed (RFC 5545), windowed to `Now-7d`..`Now+90d` (local, see [Single-Timezone Invariant](#single-timezone-invariant)), for subscribing in Google/Apple Calendar. Times are written as "floating" (no `Z`, no `TZID`) |
| `/api/sessions/history` | GET | `StudySessionDto[]` | `?days=N` (default 365) `&onlyCompleted=` (default `true`). Deliberately separate from `GetAll`, for evaluation charts and dashboard calculations (monthly quota, trend, streak) that need a caller-chosen lookback instead of the full history. `onlyCompleted=false` also returns not-yet-completed sessions, for calculations that count "all sessions" rather than only completed ones |
| `/api/settings` | GET | `UserSettingsDto` | Does not create a DB entry on first call (default object if the table is empty) |
| `/api/settings` | PUT | `UserSettingsDto` → `UserSettingsDto` | Upsert of the singleton row |
| `/api/notes` | GET | `NoteDto[]` | Sorted by `UpdatedAt` descending |
| `/api/notes/search` | GET | `NoteDto[]` | `?q=` full-text search over title+content via SQLite FTS5, relevance-sorted (`ORDER BY rank`); empty `q` → empty list. See section "Note full-text search" |
| `/api/notes` | POST/PUT/DELETE | `NoteDto` | Analogous to sessions, but `CourseId`/`SessionId` are both nullable and only validated when set (`400` with a stable message if either doesn't resolve, see "CourseId/SessionId validation on writes" above); a `PUT` that leaves either UNCHANGED is never re-validated, same frozen-at-creation exemption as sessions |
| `/api/push/publickey` | GET | `{ publicKey }` | VAPID public key for Web Push registration |
| `/api/push/subscribe` / `/unsubscribe` | POST | `PushSubscribeRequest` | Manages browser push endpoints |
| `/api/coursegoals` | GET | `CourseGoalDto[]` | All course goals ever set (incl. `Grade`) |
| `/api/coursegoals/{courseId}` | PUT | `CourseGoalDto` → `CourseGoalDto` | Upsert (target date, grade and/or completion note); client always sends the full DTO. Validated: `CourseName` not empty, `Grade` (if set) between 1.0 and 5.0. On first creation, `courseId` must additionally resolve against the user's full course universe (`400` otherwise, see "CourseId validation on writes" above) and `CourseName` is derived from the resolved course; an UPDATE of an existing goal (same `courseId`, the route's the only way to address one) never re-validates or re-derives — the name stays frozen from creation |
| `/api/coursegoals/{courseId}` | DELETE | – | 404 if no goal set |
| `/api/courses` | GET | `CourseDto[]` | Pure in-memory constant from `CourseCatalog.AppliedAICourses`, no DB access. No validation needed (not writable) |
| `/api/timerstate` | GET | `TimerStateDto` | Always returns an object (default values if never pushed: `IsRunning=false`, `SessionId=null`) |
| `/api/timerstate` | PUT | `TimerStateDto` → `TimerStateDto` | Upsert of the singleton row; called by `TimerService` on every state transition (start/pause/phase change/completion), not every second. A `SessionId` that doesn't resolve to an existing session is silently nulled server-side rather than rejected (unlike `/api/notes` above) — this fire-and-forget sync path has no caller to retry a `400` against |

## API contract

Audit finding D2: the REST API previously had no formal, machine-checkable contract - four consumer repos (studylife-app, the Home Assistant integration, studylife-ai, studylife-mcp) hand-mirror the DTOs client-side and had already drifted from the real shape. Two artifacts now exist side by side:

- **Live endpoint** — `GET /openapi/v1.json` (`Microsoft.AspNetCore.OpenApi`, wired up in `Program.cs` via `builder.Services.AddOpenApi(...)` + `app.MapOpenApi()`), always reflecting whatever is currently running. Deliberately `.AllowAnonymous()`'d against the global `FallbackPolicy` (see [Security](#security)) - the document itself isn't sensitive (public repo), and tooling needs to fetch it without a session/API key.
- **Committed contract** — [`docs/api/openapi.json`](api/openapi.json), the fixed path the consumer repos pin their generated clients against. **What refreshes it:** a plain `dotnet build` of `StudyLife.Server.csproj` - the `Microsoft.Extensions.ApiDescription.Server` package hooks a build-time generation target into the normal `Build` target (`OpenApiGenerateDocuments`/`OpenApiGenerateDocumentsOnBuild` in the csproj), which runs the app in-process to produce the document; a small `CopyOpenApiDocumentToCommittedSpec` MSBuild target then copies it from its (project-name-based, un-overridable) staging filename to the fixed `docs/api/openapi.json` path, every build, whether or not the underlying generation step itself was skipped as up to date. After changing a controller/DTO, run `dotnet build src/StudyLife.Server/StudyLife.Server.csproj` and commit the resulting diff.
- **CI freshness gate** — the `test-openapi-contract` job (`.github/workflows/ci-cd.yml`) rebuilds the Server project on every push/PR and fails with `git diff --exit-code docs/api/openapi.json` if the committed file doesn't match a fresh build - the same "regenerate and commit, or CI fails" pattern used elsewhere in this repo (e.g. `dotnet format --verify-no-changes` in `test-lint`). This is what keeps the three consumer repos' contract tests honest: a schema change without a regenerated spec fails the PR here, not silently downstream.
- **Schema quality** — controllers return typed `ActionResult<T>`, so DTO component schemas come out under their real names (`StudySessionDto`, `NoteDto`, `CourseDto`, ...) for free; the handful of endpoints that used to return a bare `IActionResult` wrapping an anonymous object (`BackupController.RestoreStatus`/`CancelRestore`, `DictationController.Transcribe`, `PushController.GetPublicKey`, `SystemController.GetCapabilities`) were given small, wire-identical response DTOs (`RestoreStatusResponseDto` and friends in `StudyLife.Shared/Dtos.cs`) purely so the generator has something to introspect. Two `IOpenApiDocumentTransformer`/`IOpenApiSchemaTransformer` implementations under `Server/OpenApi/` round out the document: `StudyLifeOpenApiSecuritySchemeTransformer` declares the two real header credentials (`X-Session-Token`, `X-Api-Key` - see [Security](#security)) as `apiKey`-type security schemes, and `StudyLifeOpenApiRequiredPropertiesTransformer` fills in each schema's `required` array from the underlying CLR property's nullability (the default generator only looks at C#'s `required`-keyword/constructor-parameter syntax, which none of these plain mutable DTOs use, so every schema would otherwise report `required: []` regardless of which fields are actually guaranteed non-null).

## Client-side services (`Client/Services/`)

- **AppStateService** — the single access point for sessions/settings/courses. Polls sessions/settings every 30s, compares a hash of the data, and on real changes fires both the granular `OnSessionsChanged`/`OnSettingsChanged` (depending on which category changed) as well as the original, cross-category `OnChange` (kept for compatibility with existing consumers like `Calendar.razor`/`Planner.razor`, which don't distinguish between the two). New consumers that want to avoid unnecessarily expensive recomputation on, say, settings changes should hook specifically into `OnSessionsChanged`/`OnSettingsChanged` instead of `OnChange` (see the dashboard example under Performance optimizations). `GetCoursesAsync()`, by contrast, caches the course catalog only once per page visit (no polling cycle needed, since the catalog practically never changes at runtime). New pages/components should hook in here instead of making their own HTTP calls.
- **TimerService** — singleton, keeps the running focus-timer state primarily in browser memory (the countdown tick still runs purely locally, no server round-trips per second). On every **state transition** (start/pause/reset/phase change focus↔break/completion), `PushStateAsync()` pushes a snapshot via `PUT /api/timerstate` (`SessionId`, `IsRunning`, `IsBreak`, `CurrentRound`, `TimerModeId`, `PhaseEndsAt` as an absolute point in time rather than a countdown in seconds, so consumers don't have to tick along). Errors are swallowed (offline fallback, as with `AppStateService`). When loading a mode, `Focus.razor` passes `_activeSession?.Id` as `SessionId` — with free-form timer use without a matching session it stays `null`.
- **NotificationService** — browser notification permission handling.

### Offline write queue (`AppStateService`)

Failed write operations (saving/deleting sessions, deleting series, saving settings) are no longer silently lost: if the HTTP call throws an exception (typically: offline), the operation lands as a `{ Type, Payload, QueuedAt }` entry in a queue persisted under the localStorage key `studylife-write-queue` (direct `localStorage.setItem/getItem` interop, no helper in `index.html`; corrupt JSON → empty queue). **Only exceptions** get queued — requests rejected by the server (e.g. 400 for `EndTime <= StartTime`) are deliberately not, since they would fail again and again on replay.

- **Replay:** at the start of every 30s poll (after the visibility check), the queue is replayed in original order; on the first network error the replay stops (the rest is left for the next poll to try again). A `bool` flag prevents parallel replays. After a successful flush, `_sessionsCache` and both hashes are invalidated so that the immediately following fetch retrieves server truth and fires the granular events.
- **Replacement rules:** settings only keep the last queued state (last write wins); session operations keep their order. Exception: a `saveSession` with Id 0 replaces an already-queued Id-0 entry with the same `StartTime`+`CourseId` (same logical session, saved offline twice — prevents duplicate POSTs).
- **Known limitation:** sessions created offline have no server id; a later offline edit/delete can't be correlated. Practically uncritical: after an offline save, the cache is invalidated and the refetch fails, so the unsynced session never even shows up in the UI (and `Calendar.razor` only deletes when `Id > 0` anyway).
- **UI signal:** `PendingWriteCount` + `OnPendingWritesChanged` are ready for a future "not synced" badge (no UI for it yet).

## Internationalization (i18n)

The UI supports 26 languages via [`Toolbelt.Blazor.I18nText`](https://github.com/jsakamoto/Toolbelt.Blazor.I18nText) (NuGet package in `StudyLife.Client.csproj`, registered in `Program.cs` via `builder.Services.AddI18nText(options => options.PersistenceLevel = PersistanceLevel.SessionAndLocal)` — language choice is retained via session/local storage, no server round-trip needed): the 24 official EU languages (English, German, French, Spanish, Italian, Portuguese, Dutch, Danish, Swedish, Finnish, Greek, Polish, Czech, Slovak, Hungarian, Romanian, Bulgarian, Croatian, Slovenian, Estonian, Latvian, Lithuanian, Maltese, Irish/Gaeilge) plus Ukrainian and Russian.

- **Text sources:** `Client/i18ntext/<Name>.<lang>.json` — flat key-value JSON files, one set of 26 language files per page/component (`IndexText`, `CalendarText`, `FocusText`, `NotesText`, `SetupText`, `StatsText`, `MainLayoutText`; 182 files total, 194 keys per language). A C# source generator (part of the same NuGet package) generates the typed `I18nText.<Name>` classes from these at build time — the JSON keys must be valid C# identifiers, there's no hand-written class for this. At runtime, the JSON files are served as static web assets under `_content/i18ntext/StudyLife.Client.I18nText.<Name>.<lang>.json` (co-hosted by the server, no extra endpoint needed).
- **Usage per component:** `@inject Toolbelt.Blazor.I18nText.I18nText I18nText`, a field `private I18nText.<Name> T = new();`, populated in the existing `OnInitializedAsync` via `T = await I18nText.GetTextTableAsync<I18nText.<Name>>(this);` (passes `this` so the component automatically re-renders on a language switch). Texts with runtime values use `{0}`/`{1}` placeholders in the JSON value and `string.Format(T.Key, value)` in code, instead of interpolating directly in the JSON.
- **Language switcher + search as a speed dial:** `.fab-dial` (formerly two separate elements: its own sidebar nav entry for search and a language switcher fixed at the top right) is now a single `position: fixed` floating action button anchored bottom right (`.app-shell` child, identical position on desktop and mobile) — `.sidebar-foot` disappears completely below 768px (`display: none`, the mobile bottom tab bar has no room there), so a switcher there would have been invisible on phones; on mobile the speed dial floats via `bottom: calc(64px + 0.75rem)` above the bottom tab bar instead of overlapping it. Clicking the main button (`.fab-main`, `_fabOpen`) unfolds two mini buttons (`.fab-actions`): search (opens `GlobalSearch`, identical to Ctrl/Cmd+K) and the current language flag (opens the existing `.lang-popup`, now `position: static` inside the speed dial instead of absolutely positioned top right, so it grows upward instead of downward). Selecting from the popup still calls `I18nText.SetCurrentLanguageAsync(code)`. A shared `.lang-popup-backdrop` closes both the unfolded mini buttons and the open language popup. `z-index: 110` is deliberately above the sidebar (`z-index: 100`/mobile `200`), otherwise the speed dial would disappear behind it.
- **Deliberately NOT affected by language switching:** number formats (`CultureInfo.InvariantCulture` for grades/percentages — e.g. the comma-decimal notation of German school grades stays independent of the UI language) and date/weekday format specifiers (`"dd.MM.yyyy"`, `"ddd"`, `"MMM"` still run through `InvariantCulture`, i.e. weekday/month abbreviations stay English regardless of the selected language) — a deliberate boundary so the number formatting that's intentionally language-independent elsewhere doesn't accidentally change too. Pure content such as course names/topics (`CourseCatalog.cs`) and motivational quotes/motivation styles (`DefaultData` in `Models.cs`) are likewise not part of the i18n text tables (that's data, not UI chrome).
- **Adding a new component:** create 26 JSON files following the naming scheme above, copy the injection/field/init block from an existing page (`MainLayout.razor` is the smallest example), replace markup strings with `@T.Key`.
- **Adding a new language:** just create `<Name>.<newcode>.json` for all 7 components (same keys as `.en.json`, translated values) — no code/Razor change needed, the source generator and runtime resolution pick it up automatically. Additionally register the new language (code, flag, native name) in `MainLayout.razor`'s `Languages` list so it appears in the popup.

## Background services (server)

**`BackgroundTaskService`** (`Services/BackgroundTaskService.cs`) — a single `BackgroundService` with one shared 30s tick loop that bundles the three previously independent reminder services (`PushBackgroundService`/`CourseGoalReminderService`/`InactivityReminderService`, merged as part of the performance optimizations, see below) plus two later-added subtasks (achievement push, SQLite maintenance) as private methods — each with its own `IServiceScope` per call and its own try/catch, so a failure in one subtask doesn't block the others:

Registered conditionally on `Worker:Enabled` (`Program.cs`, default `true`) — disabling it turns a process into a pure web-only replica with none of the subtasks below running at all. In the horizontally-scalable deployment (`docker-compose.scale.yml`/Kubernetes) this is what separates the stateless `server` replicas (`Worker:Enabled=false`) from the single `worker` replica (`Worker:Enabled=true`): without this split, every scaled-out `server` replica would independently run its own 30s tick and send every reminder/report N times. If `Worker:ReplicaCount`/`Worker:ReplicaCountSource=Kubernetes` ever raises the worker itself past one replica, each process first claims an ordinal (0..ReplicaCount-1) fresh every tick via `IWorkerShardClaim` (`RedisWorkerShardClaim` — a leased Redis key per slot, `"worker:shard:{i}"`, TTL-renewed; requires `Cache:Provider=Redis`), then `BackgroundTaskService` filters the user set to `id % ReplicaCount == ordinal`, so each user is still only ever handled by exactly one worker per tick. The default `StaticWorkerShardClaim` (ordinal always 0, `ReplicaCount` always 1) makes that filter a no-op for the common single-worker case.

The individual subtasks:

- **Push reminders** (`RunPushNotificationsAsync`) — runs on **every** 30s tick, checks for sessions starting in ≤61 minutes, and sends Web Push reminders at the thresholds configured in `UserSettingsEntity.SessionReminderMinutes` (default `[60,30,10,5,3,2,1]`). Deduplicated via `SentReminderEntity`.
- **Course-goal reminders** (`RunCourseGoalReminderCheckAsync`) — internally gated to an hourly cadence (`_nextCourseGoalReminderRun`, not a separate timer), checks all `CourseGoalEntity` records with `TargetDate` set and `CompletedAt == null`, and sends Web Push reminders at the days-before-target thresholds configured in `UserSettingsEntity.CourseGoalReminderDays` (default `[14,7,3,1,0]`). Also deduplicated via `SentReminderEntity` (key format `"coursegoal:{courseId}:reminder{days}d"`).
- **Inactivity reminders** (`RunInactivityReminderCheckAsync`) — also internally hourly-gated, determines the most recent already-started session (`StartTime <= DateTime.Now`; purely future-planned sessions deliberately don't count as "studied") and sends a motivational push reminder once more than `UserSettingsEntity.InactivityThresholdDays` days (default `5`) have passed since that session's `StartTime.Date` (or there was never a session at all). Deduplicated per calendar day via `SentReminderEntity` (key format `"inactivity:{yyyyMMdd}"`) — so during ongoing inactivity a new reminder arrives daily, not just once. Title/text are deliberately German only (server push text is not part of the i18n text tables, which only cover the Blazor UI).
- **Achievement push** (`RunAchievementCheckAsync`) — internally hourly-gated (`_nextAchievementCheckRun`), recomputes the same milestones as the dashboard (`Index.razor`, `BuildAchievements`): total hours `[25, 100, 500]`, longest streak `[7, 30, 100]` days, session count `[50, 200, 500]`, completed courses `[1, 10, 20]`, plus "all courses completed" (creditable ECTS ≥ catalog total via `CourseCatalog.CalcTotalEcts`/`CalcEctsEarned`). "Studied" means, as everywhere else, `IsCompleted || EndTime <= now`. For each newly reached milestone, **one** Web Push message goes out (title `"Achievement unlocked! 🏆"`); deduplicated **permanently** via `SentReminderEntity` (key format `"achievement:hours:100"`, `"achievement:allcourses"` etc.) — the 2-day cleanup in `RunPushNotificationsAsync` explicitly excludes `achievement:` keys, otherwise every badge would fire again after two days. The calculation deliberately duplicates the client logic (same pattern as with the Home Assistant integration): the server needs to know the thresholds itself so the push still fires with the app closed — changes to the thresholds in `Index.razor` need to be mirrored here.
- **Weekly report** (`RunWeeklyReportAsync`) — no interval gate, but calendar-based: fires once per ISO week on **Sunday from 6 pm** local time (`DateTime.Now`, container runs with `TZ=Europe/Berlin`). Deduplicated via `SentReminderEntity` (key format `"weeklyreport:{ISO-year}-W{week}"`, e.g. `weeklyreport:2026-W28`) — the key **is** the gate and survives restarts; an additional in-memory memo (`_weeklyReportSentForWeek`) only saves the 30s DB query after sending. The 2-day cleanup is deliberately allowed to age out this key (no entry in the exception list): by then the Sunday-≥6pm condition is long since false, and the next Sunday gets a new week ID anyway. Content: hours studied in the current week (Monday to now, same week-start convention as `Index.razor`), delta vs. the previous week, current streak (same semantics as `CalcStreak` in `Index.razor`, not the longest streak), and top course of the week by hours — "studied" as everywhere `IsCompleted || EndTime <= now`. For an empty week, a gentle motivational text appears instead of statistics (the report is never skipped).
- **SQLite maintenance** (`RunDatabaseMaintenanceAsync`) — internally gated **weekly** (`_nextDatabaseMaintenanceRun`; resets like all gates on process restart, i.e. "at least weekly"), runs `VACUUM;` followed by `PRAGMA wal_checkpoint(TRUNCATE);` (truncates the `-wal` file, which can otherwise grow, back to 0 bytes in WAL mode). Deliberately `VACUUM` instead of `PRAGMA incremental_vacuum`, because the DB runs with SQLite's default `auto_vacuum=NONE`, where `incremental_vacuum` would be a no-op; and deliberately the checkpoint **after** the `VACUUM`, because in WAL mode `VACUUM` also commits via the `-wal` file, and the main DB only shrinks with the next checkpoint. `VACUUM` must not run inside a transaction (`ExecuteSqlRawAsync` doesn't start one) and only holds the DB exclusively for a short time — uncritical given the weekly cadence and `busy_timeout=5000`.

All three reminder subtasks freshly read the current thresholds from the (single) `Settings` row on **every** check cycle (`ReminderSettings.cs` parses the comma-separated strings with a fallback to the default values if empty/invalid — e.g. for existing installations predating the `AddReminderSettings` migration). So there's no need to restart after a change in Setup; the new values take effect from the next cycle. A single `WebPushClient` (lazy via `GetPushClient()`) and a per-tick memoized subscriptions fetch are reused across all push subtasks.

## Dashboard weekly trend & course-goal overview (`Pages/Index.razor`)

## Recurring appointments (`Pages/Calendar.razor`)

When creating a **new** session (not when editing), "Repeat" can additionally be enabled, with three controls: interval (every week / every 2 weeks / every 3 or 4 weeks, `_formRepeatIntervalWeeks`), an end date (`_formRepeatUntil`), and a multi-select of weekdays (`_formRepeatWeekdays`, a Mon–Sun chip picker — the default is solely the weekday of the start date, so that the unchanged behavior "same weekday every week" remains the default case). `SaveSession` first creates the first session as usual via `State.SaveSessionAsync` and then scans **day by day** (no longer in `+7-day` jumps) from the following day up to the end date: a day produces a session if its weekday is contained in `_formRepeatWeekdays` **and** its week block (Monday-anchored, `occurrenceWeekMonday`) falls into the chosen cadence according to `weeksSinceStart % intervalWeeks == 0`. ## Manual theme switcher (`Pages/Setup.razor`, `Shared/MainLayout.razor`)

`UserSettings.Theme`/`UserSettingsDto.Theme` (values `"system"` | `"light"` | `"dark"`, default `"dark"`) already existed in the data model from earlier rounds, but was never read anywhere — the toggle in Setup.razor is the first actual use of it. Implemented without any server-side change, purely via CSS specificity:

- `app.css` defines the dark values in the normal `:root`, light values in `@media (prefers-color-scheme: light) { :root {...} }` (system behavior, unchanged) — **additionally** the same light/dark values again under `:root[data-theme="light"]`/`:root[data-theme="dark"]`. An attribute selector has higher specificity than a plain `:root` inside the media query, so it wins regardless of the system setting as soon as the attribute is set.
- `index.html` defines `applyTheme(theme)` (JS): sets `data-theme` on `<html>` for `"light"`/`"dark"`, removes the attribute for `"system"` (then the media query takes over again).
- `Setup.razor`'s `SetTheme(theme)` calls `applyTheme` immediately via JS interop (live preview without reload) and saves directly via `State.SaveSettingsAsync` (no separate save button, same pattern as the course-goal date).
- `MainLayout.razor` calls `applyTheme(settings.Theme)` once in `OnInitializedAsync`, so the saved choice takes effect immediately even after a reload (not only when visiting the Setup page).
- Since no write path existed before this change, but `Theme` was consistently stored as `"dark"` from the client model default, a user whose browser is set to "light" may initially see forced dark mode after this update, until they tap "System" or "Light" once — a one-time, expected effect on first use of the new control, no further migration planned (single-user app).
- **Bugfix (Android Chrome, especially installed PWA):** the switcher visibly did nothing on some Android devices, because neither `index.html` nor `app.css` declared a `color-scheme`. Without this declaration, Chrome's "Auto Dark Theme" (or "Simplified Dark Theme") kicks in and forcibly recolors the page at the rendering level according to the system state — completely independent of our `data-theme` attribute and the CSS variables, which remained ineffective as a result. Fixed via `<meta name="color-scheme" content="dark light">` in `index.html` plus the matching CSS property `color-scheme` in `:root`, in the `prefers-color-scheme: light` block, and in both `:root[data-theme="..."]` overrides (signals to the browser "this page manages light/dark itself, no auto-correction needed"). Additionally, the service worker cache strategy (`service-worker.published.js`/`service-worker.js`) was versioned (`CACHE_NAME` with a suffix, old cache keys are deleted in `activate`) as a safeguard against a randomly stale cache entry frozen by a failed network request (more likely on mobile data than on stable Wi-Fi/wired).

## Note full-text search via SQLite FTS5 (`Controllers/NotesController.cs`, migration `AddNotesFts`)

Note search runs server-side via an **FTS5 full-text index** instead of a `LIKE`/substring scan:

- **Table:** `NotesFts` is a virtual FTS5 table as an **external content table** over `Notes(Title, Content)` (`content='Notes'`, `content_rowid='Id'`) — it only stores the inverted index, not the text itself again. Three triggers on `Notes` (`Notes_fts_ai`/`_ad`/`_au`, AFTER INSERT/DELETE/UPDATE, following the pattern documented in the SQLite docs with the special `'delete'` command) keep the index in sync on every write — regardless of whether the writer is EF Core, the HA integration, or manual SQL.
- **Raw-SQL migration, deliberately without an EF entity:** `NotesFts` and the triggers are created in the `AddNotesFts` migration exclusively via `migrationBuilder.Sql(...)` (including initial population from existing rows); `Down()` drops the triggers + table again. EF Core knows neither virtual tables nor triggers as first-class concepts — the FTS table therefore **deliberately does not** appear in the model snapshot (the migration's snapshot is unchanged from the previous migration). Anyone who changes the Notes schema in the future (renaming columns, rebuilding the table) must carry the triggers + `NotesFts` along via raw SQL in the same migration; EF doesn't do that automatically.
- **Endpoint:** `GET /api/notes/search?q=...` (`NotesController.Search`) first translates the raw user input into a safe MATCH expression (`BuildFtsMatchQuery`: each whitespace-separated word becomes a prefix phrase `"word"*`, embedded `"` are doubled — raw input like `-`, `(`, or a lone `"` would otherwise throw an FTS5 syntax error) and then queries via `FromSqlRaw` with a parameterized MATCH: `SELECT n.* FROM Notes n JOIN NotesFts f ON f.rowid = n.Id WHERE NotesFts MATCH {0} ORDER BY rank` (bm25 relevance instead of `UpdatedAt`). An empty/whitespace `q` returns an empty list; the DTO format is identical to `GET /api/notes`. A course filter is deliberately **not** part of the endpoint — the client continues to apply that locally to the search result.
- **Client:** see "Search & filter" above (300ms debounce, immediate local filter as an interim result/offline fallback, empty search = normal list with no round-trip).

## Custom timer modes (`Pages/Setup.razor`, `Pages/Focus.razor`, `Models/Models.cs`)

The Pomodoro-style timer modes on the Focus page were previously only the five built-in ones from `DefaultData.TimerModes` (IDs 1-5). Users can now create their own modes (e.g. "Deep Work 90/20"):

- **Storage:** `UserSettingsEntity.CustomTimerModes` (migration `AddCustomTimerModes`, one column, default `""`) as a **JSON array** of small objects — `[{"id":100,"name":"Deep Work","focusMinutes":90,"breakMinutes":20,"rounds":1}]`. Deliberately JSON instead of the otherwise-usual comma-separated strings (`SelectedCourseIds` & co.), because mode names are free text and may contain commas/semicolons. IDs start at 100 and are assigned via `max(existing custom IDs, 99) + 1` — collision-free with the built-ins. The field runs through the entire settings chain analogous to `TargetGraduationDate` (entity → DTO → `SettingsController.ToDto`/`Save` → client `UserSettings` → `AppStateService.FromDto`/`ToDto`/`ComputeSettingsHash`); `SettingsController.Save` only checks a maximum length (4000 characters) to protect the singleton row.
- **Client-side parsing:** a static helper class `CustomTimerModes` in `Models.cs` (`Parse`/`Serialize`/`NextId`/`Combined`). `Parse` is tolerant: empty/invalid JSON yields an empty list (the codebase's fallback style); values are clamped on parsing (focus 5-180, break 0-60, rounds 1-10). Custom modes become full-fledged `TimerMode` instances with fixed defaults (emoji "⚙", style `custom`, green gradient) — `TimerService` is purely data-driven (no switch on mode IDs) and needs no adjustment.
- **Setup UI:** `Components/Setup/SetupTimerModesCard.razor` (after the graduation-date card) lists custom modes with a delete button and offers an add row (name max. 24 characters, focus/break/rounds as number fields with clamping). The parent (`Setup.razor`) owns the parsed list (`_customModes`), assigns IDs, and serializes back into `_settings.CustomTimerModes` on every change — saved only via the existing save button (deferred, like study window/graduation date).

## Backup & export (`Controllers/BackupController.cs`, `Services/DatabaseBackupService.cs`)

Two ways to get your own data out of the app, both under Setup → "Backup & export" (`Components/Setup/SetupBackupCard.razor`, plain download links, no JS interop needed):

- **`GET /api/backup/database`** delivers a consistent copy of the SQLite file for download. A plain `File.OpenRead` of the live file would be unsafe in WAL mode (not-yet-checkpointed writes sit in the separate `-wal` file and would be missing from a plain file copy — verified in a scratch test). Instead, `DatabaseBackupService.CreateBackup` uses SQLite's online backup API (`SqliteConnection.BackupDatabase`), which internally wraps `sqlite3_backup_init/step/finish` and is therefore WAL-safe.
- **`GET /api/backup/export`** delivers a human-readable JSON export of the actual user data ("v2" format, audit finding M4 — a previous version was both incomplete and inconsistently serialized, see below) via the same `ToDto` projections as the normal controllers (using `internal static` instead of `private static` for this purpose), plus three export-only DTOs (`StudyProgramExportDto`/`CourseGroupExportDto`/`CustomCourseExportDto` in `StudyLife.Shared`) for the tables that have no id-carrying API DTO of their own. Every user-owned table is included: `Sessions`, `Notes`, `CourseGoals`, `CourseResources`, `Settings`, `StudyPrograms`, `CourseGroups`, `CustomCourses`, `SessionTemplates`. Deliberately still excluded: `PushSubscriptions` (this browser's endpoint registrations, not transferable), `SentReminders` (internal dedup bookkeeping), `TimerState` (transient live state), and every auth/infrastructure table (`AuthUsers`, `PasskeyCredentials`, `AuthSessions`, `RecoveryCodes`, `SystemSecrets`, `AiKeyOutbox`) — not user data, and re-importing a session/passkey/setup-code row would be either meaningless across accounts or a security hole. The envelope carries `formatVersion` (currently `2`), `exportedAt`, and `appVersion`, and is serialized with the exact same `JsonSerializerOptions` the MVC pipeline itself uses for every other controller (`BackupController._jsonOptions`, injected via `IOptions<JsonOptions>`) — the fix for the former casing bug: `Export()` used to build the envelope as an anonymous object and serialize it with a hand-rolled `JsonSerializerOptions` that had no naming policy, so the outer wrapper (coincidentally already camelCase field names) looked fine while every nested DTO came out PascalCase, diverging from the rest of the API's wire format. See `ApiContractTests.cs` (`BackupExportCasingTests`) for the regression test.
- **`POST /api/backup/import-json`** (audit finding M4) accepts a v2 export (or a legacy v1 file — see below) and performs a **full replace of the calling user's own data**: every row this user owns in every table above is deleted, then the file's rows are re-inserted with freshly assigned ids, all inside one transaction. `[Authorize(Policy = SessionOnly)]`, but deliberately **not** owner-gated like the raw DB endpoints below — it only ever touches the caller's own rows (same reasoning as `GET .../export` already being open to every user), so any logged-in user may run it; a real passkey session is still required so a bare API key (e.g. Home Assistant's) can't wipe an account by itself. Capped at 64MB (`[RequestSizeLimit]` plus an explicit `Request.ContentLength` check for defense in depth) — far smaller than the raw 512MB SQLite restore, since a JSON export is text.
  - **Id remapping** is the reason this isn't a naive bulk insert: `CustomCourseEntity` rows get a *new* database id on insert, so every place that references the externally shifted id (`StudyProgramCatalog.CustomCourseIdOffset` + old id) — `Sessions`/`CourseGoals`/`CourseResources`/`SessionTemplates`' `CourseId`, `Settings`' `SelectedCourseIds`/`CompletedCourseIds` — is rewritten to the new shifted id. Likewise `CourseGroup`→`StudyProgram`, `CustomCourse`→`StudyProgram`/`CourseGroup`, `Settings.ActiveStudyProgramId`→`StudyProgram`, `Note.SessionId`→`Session`, and `Note.RelatedNoteIds`→`Note` (the last two only exist after their target table's own insert pass, hence the import order: study programs → elective groups → custom courses → session templates → sessions → notes (two passes, since a note's `RelatedNoteIds` can reference a note inserted after it) → course goals → course resources → settings). Built-in catalog course ids (below the offset) always pass through unchanged and unvalidated, matching how the rest of the app already treats them.
  - **Dangling references** (an unknown custom-course/study-program/group/note/session id — e.g. a partial or hand-edited export file) are dropped tolerantly instead of failing the whole import: either the whole referencing row for a required field (e.g. `Session.CourseId`) or just the one dangling entry for an optional field/comma-separated list (e.g. `Settings.SelectedCourseIds`, `CommaSeparatedIds`-style tolerance). The response (`BackupImportResponseDto`) reports per-table `imported`/`dropped` counts so nothing vanishes silently.
  - **v1 compatibility:** a legacy export (no `formatVersion` property, PascalCase nested DTOs) is accepted best-effort — ASP.NET Core's case-insensitive JSON binding (`JsonSerializerDefaults.Web`, unchanged in `Program.cs`) recovers the PascalCase fields regardless, and a missing `formatVersion` deserializes to its `int` default `0`, which `ImportJson` explicitly treats as "legacy, proceed". Tables that don't exist in a v1 file (`StudyPrograms`/`CourseGroups`/`CustomCourses`/`SessionTemplates`) simply import nothing instead of failing the request. Any other, unrecognized `formatVersion` (e.g. a future format this server version doesn't understand) is rejected with `400`.
- **Weekly auto-dump:** `BackgroundTaskService` calls `DatabaseBackupService.CreateWeeklyBackup` (same maintenance cadence as the SQLite VACUUM task) and writes to `app_data/backups/studylife-{yyyyMMdd}.db`, keeping only the last 4 files (deletes older ones based on the lexicographically = chronologically sortable filename).
- All endpoints live under `/api` and thereby automatically inherit the API-key protection (the middleware operates path-based, not per-controller); on a public demo instance (`DEMO_MODE=true`, see below) `/api/backup` is blocked ENTIRELY (any method, including the new import endpoint) before it even reaches routing.
- **Optional password encryption of the `.db` download** (`Services/BackupEncryptionService.cs`): AES-256-GCM (authenticated encryption, no separate HMAC needed) with a key derived from the password via PBKDF2-HMAC-SHA256 (210,000 iterations, OWASP recommendation) — plain `System.Security.Cryptography`, no new dependency. File format: `[Magic "SLBKENC1" 8 bytes][Salt 16 bytes][Nonce 12 bytes][Tag 16 bytes][Ciphertext]`, salt/nonce freshly randomized per encryption. The password is never persisted anywhere (not in `UserSettingsEntity`, no file) — a pure runtime parameter, like an "encrypt as zip" dialog. `POST /api/backup/database/encrypted` (password in the JSON body, never as a URL query — unlike the former `?apiKey=` rotation key, this is a self-chosen user secret) returns the encrypted file; since this is a POST with a file response (no native `<a download>` possible), `SetupBackupCard.razor` reads the response as a stream and hands it to the collocated JS module `SetupBackupCard.razor.js` (`DotNetStreamReference` → blob URL → programmatic download), analogous to `Focus.razor.js`. `POST /api/backup/restore` detects an encrypted upload by its magic header (`BackupEncryptionService.IsEncryptedFile`) even before the actual validation, decrypts into a separate temp file when a `password` form field is present, and hands THIS unchanged to the existing `DatabaseRestoreService.Validate`/`Stage` pipeline — no second restore logic. A missing or wrong password returns `400 { error, encrypted: true }` (AES-GCM's auth tag makes a wrong password and a tampered file indistinguishable, hence a shared `BackupDecryptionException`); `SetupRestoreCard.razor` uses the `encrypted` flag for a reactive second step in the existing confirmation modal (the password field appears only after this response, instead of showing it to all users from the start).

## Calendar series deletion (`Pages/Calendar.razor`)

Recurring sessions (see "Recurring appointments" above) were previously completely independent rows with no grouping concept. `StudySessionEntity`/`-Dto`/`StudySession` now have an optional `RecurrenceGroupId` (a `Guid.NewGuid().ToString()`, generated once when creating a series and written to the first AND every weekly-repeated session — a one-off session remains `null`). This lets you choose the scope precisely when deleting: the delete-confirmation dialog shows three options instead of the usual two for a session WITH `RecurrenceGroupId` ("Only this session" → the normal single `DELETE api/sessions/{id}`, "This and all following" → a new `DELETE api/sessions/series/{groupId}?fromDate=` with the clicked session's start date, "Entire series" → the same endpoint without `fromDate`). Sessions without `RecurrenceGroupId` keep exactly the previous two-click behavior. There is deliberately **no** "edit series" feature — editing a single instance still works independently as before, only deletion is aware of the grouping.

## Achievements (`Pages/Index.razor`)

Another full-width dashboard tile (`.card-achievements`) shows permanent milestone badges — deliberately designed as an **all-time best** (not "current status"), so that a badge once unlocked doesn't disappear again due to later inactivity. `BuildAchievementsAsync` loads its own, very long `GET /api/sessions/history?days=3650` for this (`AchievementHistoryDays` constant, ~10 years) — deliberately separate from the existing `HistoryDays = 400`, since the latter is tuned for monthly quota/trend/streak/balance check and would undercount multi-year study histories for a "total hours" badge. Badge categories (`Achievement` record with `Icon`/`Name`/`Unlocked`/`Current`/`Threshold`):

- **Hours** (⏱, thresholds 25/100/500h) and **sessions** (✅, 50/200/500) — simple sums/counts over the full history.
- **Streak** (🔥, 7/30/100 days) — unlike the 7-day streak strip in `.card-today-focus` (which shows the *current* streak), `CalcLongestStreak` uses the **longest ever achieved** streak (`Distinct().OrderBy` over all study days, longest run of consecutive calendar days), matching the "once unlocked, stays unlocked" principle.
- **Courses** (🎓, 1/10/20 completed) and **all courses completed** (🏆) — from `settings.CompletedCourseIds.Count` and `_ectsEarned >= _ectsTotal` respectively (reused from the study-progress tile, no additional request).

Locked badges are grayed out (`.achievement-badge.locked`, `opacity: 0.35; filter: grayscale(1)`) rather than hidden, so it stays visible what one is still working toward.

## Desired-graduation tile (`Pages/Index.razor`, `Components/Dashboard/DashboardGraduationGoalCard.razor`)

The inverse of the ECTS forecast: instead of "when will I be done at the current pace?", the tile answers "how many study hours per week do I need to be done by the desired graduation date (`UserSettings.TargetGraduationDate`, see the Setup section)?" Computed in `BuildForecast` from exactly the same intermediate values as the forecast: `remainingEffortHours = baselineWeeksNeeded × referenceWeeklyHours` (semester baseline × 27.5h reference workload) spread over `weeksUntilTarget = (target date − today) / 7`; "on track" means that the same 8-week pace (`recentWeeklyHours`) that also refines the forecast meets the required workload (badge `badge-ok`/`badge-warn`, same look as the quota tiles, required hours formatted with one decimal place and a comma). The tile only appears with a target date set and shares all the forecast's guards (open ECTS > 0, semester structure present); an elapsed target date shows an "expired" notice instead of negative required hours. Since `BuildForecast` was previously skipped on settings-only reloads (target-date changes would otherwise only arrive via poll with the next session refresh), `LoadDataAsync` now recomputes the forecast + tile in this case using the cached long-term history — cheap, no repeated ~10-year fetch.

## Productivity-hint tile (`Pages/Index.razor`, `Components/Dashboard/DashboardProductivityHintCard.razor`)

`BuildProductivityHint` translates study rhythm into a concrete suggestion for the day: over the already-loaded 400-day `completedHistory`, hours studied per time-of-day bucket are summed — with exactly the same bucket boundaries and the same start-hour assignment as `Stats.razor`'s `BuildWeekdayAndTimeOfDay` (0–6/6–9/9–12/12–15/15–18/18–21/21–24, no additional request). The tile only appears with a reliable enough data basis (≥ 10 studied sessions and the best bucket ≥ 30% share) and knows three states: a today's session overlaps the best time window → confirmation badge; nothing planned yet and the window cut by `StudyWindowStartHour`/`EndHour` isn't already entirely in the past today (and today is a study day per `StudyDays`) → plan suggestion with a `/calendar` link; otherwise just the neutral insight with no call to action.

## What counts as "studied"? (`Controllers/SessionsController.cs`, `Pages/Index.razor`, `Pages/Stats.razor`, `coordinator.py`)

`IsCompleted` is only set on a full run-through of the focus timer (`Focus.razor`'s `OnSessionComplete`). Balance check, streak, achievements, and the evaluation page originally filtered strictly on `IsCompleted == true` — a session planned in the calendar but carried out without the in-app timer (e.g. studying with a book by the lake) thus remained invisible to all statistics, even though it had actually happened. Bugfix: "studied" now means everywhere **`IsCompleted == true` OR the planned end time is already in the past** (`s.EndTime <= DateTime.Now`) — the timer remains the way to mark a session as done *early*, but nobody has to use it for an already-elapsed session to count. For all DTO-based C# call sites, the predicate now lives centrally in `StudyMetrics.IsStudied` (see the section "Shared metrics logic" below); only the sites that work on the client model `StudySession` instead of the DTO (e.g. the focus score over `_todaySessions`), and the Python side (HA), still apply the rule inline. Affected sites that consistently apply this semantics:

- `SessionsController.GetHistory`'s `onlyCompleted` filter (feeds, among others, `Index.razor`'s achievements fetch and `Stats.razor`'s heatmap/donut/weekday/monthly-breakdown, which don't override the parameter).
- `Index.razor`'s `completedHistory` (streak, mini-donut, balance check, "last completed", 7-day streak strip) and the "done"/"✓" display of today's sessions (`IsDone(s)` helper instead of `s.IsCompleted` directly).
- `Stats.razor`'s per-course hours/sessions count (`completedSessions` in `OnInitializedAsync`).
- `coordinator.py`'s `completed_history` list (feeds `_calc_streak`, `_calc_longest_streak`, `_calc_neglected_course`, `_calc_achievements`) and `_calc_course_hours` (now receives `now` as a parameter).

Deliberately **not** changed: `AppStateService.GetActiveSessionAsync`/`GetUpcomingSessionAsync` and their HA counterparts in `coordinator.py` (active/next session), since there `IsCompleted` answers a different question ("was the timer ended early", not "does this count as studied"), and the time-window conditions (`StartTime <= now <= EndTime` or `StartTime > now`) already ensure that past sessions don't show up there anymore anyway.

## Shared metrics logic (`StudyLife.Shared/StudyMetrics.cs`)

Streak, forecast, quota, and average-grade calculations historically existed as three hand-maintained copies: `Index.razor`, `Stats.razor`, and (for achievement push/weekly report) `BackgroundTaskService.cs` each implemented the same logic locally, with "keep in sync on changes there" comments as the only safeguard. These copies have been merged into a static class of pure functions in `StudyLife.Shared` (where the code shared by client **and** server already lives with `Dtos.cs`/`CourseCatalog.cs`):

- `IsStudied(StudySessionDto, now)` — the "studied" definition (see the section above).
- `WeekStartOf(date)` — Monday week start (modulo offset), previously the `dowOffset` pattern scattered across both sides and the server.
- `CalcStreak(studyTimes, today)` — current streak (anchored on today, otherwise yesterday; lives until midnight).
- `CalcLongestStreak(studyTimes)` — longest streak ever achieved (distinct calendar days, unbroken sequence).
- `CalcWeightedAverageGrade(gradedCourses)` — ECTS-weighted average grade (falls back to unweighted if the ECTS sum is 0, `null` for empty input); also used by `Stats.razor`'s per-semester grade history.
- `CalcForecast(...)` → `ForecastResult` — the semester-based + pace-adjusted ECTS forecast. Besides date/availability, also returns `BaselineWeeksNeeded`/`RecentWeeklyHours`/`ReferenceWeeklyHours`, so `Index.razor`'s desired-graduation tile (the inverse calculation "how many h/week until the target date?") can sit as a thin wrapper on top without recomputing the intermediate values — this extra block deliberately stays page-specific in `Index.razor`.
- `CalcQuota(hours, targetMin, targetMax)` + `ProrateMonthlyTarget(...)` — percentage/warning/hours-missing against a min/max target (115% bar scale), identical for weekly (without proration) and monthly quota (target prorated by elapsed weeks).

Consumers: `Index.razor` (streak, quotas, average grade, forecast, weekly groupings of achievements/best values), `Stats.razor` (overall + per-semester average grade, forecast, longest streak, weekly buckets, "studied" filter), and `BackgroundTaskService.cs` (achievement streak, weekly-report streak/week-start). UI presentation (i18n format strings, `"12h 30m"` labels, field assignments) stays on the pages. **Not** included: `coordinator.py` — the Home Assistant integration is Python and remains a deliberately parallel implementation with identical semantics, which must still be manually kept in sync with changes to `StudyMetrics`.

`StudyMetrics.Dashboard.cs`/`StudyMetrics.WeeklyReport.cs` (same partial class, split by concern like `BackgroundTaskService.*.cs`) extend this with the dashboard-aggregate functions that used to be inline, page-only code: `CalcCourseHours` (`Stats.razor.cs`/`Report.razor.cs`, two formerly independent copies of the same loop), `CalcNeglectedCourse` (`Index.Insights.razor.cs`), `CalcTopicsProgress`/`CalcUpcomingCourseGoals` (`Index.razor.cs`), `CalcMonthComparison` (`Index.Forecast.razor.cs`), and the new `CalcLastCompletedWeekReport` (modelled on `BackgroundTaskService.Reports`'s weekly-report push, but for the last COMPLETED Mon-Sun week instead of the current one, so it's always available - see the Metrics API section below). `AchievementCatalog.BuildInputs` similarly unifies the achievement-tier input gathering that `Index.Achievements.razor.cs` and `BackgroundTaskService.Reports`'s `RunAchievementCheckAsync` used to compute independently. Every client page still calls these in-process (offline capability preserved) - see "Metrics API" for the server-side consumer.

## Metrics API (`Controllers/MetricsController.cs`, `docs/api/metrics-contract-v1`)

Owner decision: every metric the app computes is now computed in exactly ONE place - `StudyLife.Shared`, served by the server via `GET /api/metrics/summary` (streak, quotas, hours, ECTS, forecast, month/year comparison, neglected course, last-completed-week report, per-course hours, topic progress, upcoming goals) and `GET /api/metrics/achievements` (all 44 achievement tiers). This closes the gap noted below under "Typical pitfalls": a non-.NET consumer (the Home Assistant integration, `studylife-hacs`) no longer has to re-implement the calculations in a second language and manually keep them in sync - `coordinator.py`'s streak/quota/forecast/ECTS parity with `coordinator.py`'s own remaining hand-written pieces is still tracked by the golden-fixture pair (`docs/api/metrics-fixtures.json` + `MetricsGoldenFixtureTests.cs`), extended to cover the new endpoint-level response shape too (`MetricsControllerTests.cs` asserts the wire response against the same fixtures). The client app is UNCHANGED in spirit: it keeps calling the same `StudyMetrics`/`AchievementCatalog` functions directly, in-process (offline capability, zero duplication - it's the same code the endpoint calls server-side). `program`/`now` query params follow the same resolution convention as `GET /api/courses` (0/absent/explicit id), except an explicit non-existent programme id is a 404 here (a metrics response for a programme that doesn't exist would be actively misleading, unlike `GET /api/courses`'s harmless cache-buster fallback). Scope: `ApiKeyScopes.Ha` gains both endpoints (the coordinator polls them instead of computing).

## Configurable reminder thresholds (`Components/Setup/SetupReminderSettings.razor`, `Services/ReminderSettings.cs`)

The three server reminder services (see above) previously had their thresholds hardcoded as `static readonly`/`const` fields in code. They now live in `UserSettingsEntity`/`UserSettingsDto`/`UserSettings` as plain strings (`SessionReminderMinutes`, `CourseGoalReminderDays`, each comma-separated, e.g. `"60,30,10,5,3,2,1"`) or `int` (`InactivityThresholdDays`), and are directly editable in Setup under "Reminder thresholds" (chip-based multi-select for the two comma lists with predefined thresholds, plus a number input, saved via the existing save button — no autosave, analogous to auto-switch minutes). The chip presets are: session reminders `[60,30,15,10,5,3,2,1]` minutes, course-goal reminders `[30,14,7,3,1,0]` days. Custom values outside these presets (added by users via the old text-input UI) are preserved and displayed when saving.

`Services/ReminderSettings.cs` is the single parsing location for the comma-separated strings (`ParseSessionReminderMinutes`/`ParseCourseGoalReminderDays`/`GetInactivityThresholdDays`) and is called freshly by all three reminder services on **every** check cycle (no caching) — values that are empty, unparsable, or (for existing installations predating the `AddReminderSettings` migration) still at the column default `""`/`0` automatically fall back to the old hardcoded values (`[60,30,10,5,3,2,1]`/`[14,7,3,1,0]`/`5`). `SettingsController.ToDto` applies the same fallback when reading, so the Setup UI also shows sensible defaults on first open instead of empty fields.

  - **Bugfix 1 (JS error on click):** `Calendar.razor` initially called `JS.InvokeVoidAsync("print")` directly. In some mobile contexts (especially inside the installed PWA), `window.print` is either not defined or throws when called — uncaught, this ended up as Blazor's "unhandled exception" banner. Now wrapped in `printPage()` (`index.html`, try/catch, checks `typeof window.print === 'function'`, returns `bool` instead of throwing); `PrintWeek()` additionally catches this client-side and briefly shows a hint text (`.print-unsupported-hint`, 2.5s, same transient-flag pattern as `_icsCopied`/`_testSent` in Setup.razor) instead of an error message when printing isn't supported.
  - **Bugfix 2 (error banner in the printed result, not on click):** `#blazor-error-ui` (Blazor's default error banner in `index.html`) had **no** CSS rule in this project hiding it by default — this went unnoticed in the normal browser window because `body`/`html` are clamped to a fixed height via `overflow: hidden`, and the banner (browser default `display: block`) simply sat below the visible area. The `@media print` block lifts exactly this clamping (`overflow: visible` on `.main-content` etc.), which made the actually hidden, but technically always-rendered, banner ("An unhandled error has occurred") suddenly visible in the print result — **without any real error ever occurring**. Fixed by adding the missing default CSS for `#blazor-error-ui` (fixed-positioned, `display: none` as default, exactly the standard snippet from the Blazor project template — display on a real error is handled by Blazor's own JS via `style.display = 'block'`, no custom wiring needed) plus an additional explicit `display: none !important` inside the `@media print` block as a second safeguard.
- **Weekly swipe gesture (mobile):** besides the header, the calendar grid (`#cal-outer`) also reacts to horizontal swipe gestures — implemented in JS (`initCalendarSwipe` in `index.html`, passive touch listeners, callback via `DotNetObjectReference` on `SwipeNextWeek`/`SwipePrevWeek`), because Blazor touch events don't provide scroll position. A week change only triggers if the horizontal scroll container was already at the corresponding edge at the **start** of the gesture (swipe left → next week only at the right edge, swipe right → previous week only at the left edge), plus a minimum distance of 60px and a dominant horizontal axis — panning within the week thus still scrolls natively, paging only happens at the edge.
- **Day view (mobile):** a week/day switcher in the calendar header (`_viewMode` in `Calendar.razor`, `.cal-view-switch` in the same style as the theme switch) optionally renders only `_currentDay` as a single, full-width column — `.cal-inner.cal-day-mode` lifts the minimum width so no horizontal scroll is needed anymore on phones. On narrow viewports (≤768px, detected once via `isNarrowViewport()` in `index.html`, wrapped in try/catch with week view as fallback), day view is the default; a manual toggle choice wins for the session but isn't persisted. Arrow buttons, header swipe, and the `SwipeNextWeek`/`SwipePrevWeek` gestures navigate mode-dependently (±1 day instead of ±7), with `_weekStart`/`_days` carried along when crossing week boundaries, so switching back to week view stays seamless.
- **Automatic topic suggestion:** when creating a **new** session, `SuggestTopic()` automatically suggests the first not-yet-checked-off topic of the selected course (`CourseDto.Topics` minus `CourseGoalDto.CompletedTopics`, same parsing logic as Setup.razor). Pure prefill: only kicks in if the topic field is still empty, so it never overwrites an already-entered value. Triggered when opening the "new session" modal (`OnDayClick`) and on every course change (`OnFormFieldChanged`).

## ECTS forecast & month/year comparison (`Pages/Stats.razor`, `Pages/Index.razor`)

- **ECTS forecast ("Done at current pace by ..."):** **Bugfix (v2):** the first version calculated linearly starting from the earliest `CourseGoalDto.CompletedAt` among all course goals — this produced absurdly optimistic dates for anyone who marks already-completed courses as "completed" in the app only after the fact (all `CompletedAt` timestamps then land near "today", making it look mathematically as if years of ECTS were earned within a few days). Now semester-based instead of timestamp-based: `ECTS per semester = total ECTS / number of semesters in the catalog (CourseDto.Semester.Max())`, `baseline weeks = open ECTS / ECTS-per-semester × 26` (one semester = 6 months ≈ 26 weeks). This structural baseline estimate is then refined with the **actual** study rate of the last 8 weeks: `pace factor = avg. hours/week (last 8 weeks) / 27.5` (27.5 = the mean of the existing 25-30h weekly goal), clamped to `[0.25, 3.0]` to avoid extreme distortion with very low/high activity; `final weeks = baseline weeks / pace factor`. Without semester structure in the catalog or already at 100% ECTS (`_forecastAlreadyDone`), no date is shown, but instead "not enough data" or its own "already done" message. The formula now lives centrally in `StudyMetrics.CalcForecast` (see "Shared metrics logic" above) and is called from both pages (Stats.razor as its own row in the study-progress tile, Index.razor as a short form in `.card-progress`). The Home Assistant integration (`coordinator.py`'s `_calc_forecast`) was updated to match exactly (see below).
- **Month/year comparison:** a new dashboard tile `.card-month-comparison` shows the current calendar month's hours as well as the delta vs. the previous month and (if data reaches back far enough) vs. the same month last year. Uses `Index.razor`'s ~10-year history already loaded for achievements for this (`_allTimeHistory`, hoisted out of `BuildAchievementsAsync` in `LoadDataAsync` so both features can share it — no additional request). The year comparison is only shown if the oldest ever logged session reaches back before the 1st of the same month last year (`_monthCompHasYearData`) — otherwise a misleading "0h" would appear instead of simply not showing the row. `Stats.razor` additionally gets a compact month-comparison row in its "total" tile, but there **only** the previous month (its 371-day window doesn't reliably reach far enough for a year comparison).

## Home Assistant integration

Under [`studylife-homeassistant`](https://github.com/lukislp/studylife-hacs) (a separate, MIT-licensed repository) lives a custom HACS integration that polls against the REST API documented above and maps practically the entire dashboard/evaluation metrics surface (active/next session including exact start/end as timestamp sensors, weekly/monthly statistics including previous week/delta, streak, quotas, hours per course, weighted average grade, ECTS progress, next-due course goal (+ list of the next 5), balance check (most-neglected active course), the real course catalog, live timer phase) as sensors/binary sensors/calendars in Home Assistant. Several calculations are deliberately duplicated 1:1 from the client in `coordinator.py` and must be kept in sync with changes there: `_calc_average_grade` (↔ `Stats.razor`, now likewise ECTS-weighted), `_calc_ects_progress` (↔ `Stats.razor`'s study-progress tile), `_calc_course_hours` (↔ `Stats.razor`'s per-course list), `_calc_streak`/monthly/weekly hours (↔ `Index.razor`'s streak/monthly quota/week comparison, since this fix also via `GET /api/sessions/history` instead of the too-narrow `/api/sessions` window, `async_get_session_history` in `api.py`), `_calc_neglected_course` (↔ `Index.razor`'s balance-check tile), `_calc_upcoming_course_goals` (↔ `Index.razor`'s course-goal tile), `_resolve_courses` in `sensor.py` (↔ `Index.razor`'s course pills, now possible thanks to `/api/courses`). A `select.studylife_active_course` entity (`select.py`) maps the active (selected, not completed) courses as a dropdown — a pure picker without an API side effect (state is only held locally via `RestoreEntity`), intended as a complement to the services below: `services.yaml` previously only offered a number/text input for `course_id`/`course_name`, but which courses are currently active differs per user/point in time and can't be mapped as a selection list in a static `services.yaml` — hence the dynamic select entity as a workaround, whose `course_id` attribute can be plugged directly into automations. To match, `create_session`/`update_session`/`set_course_goal` now automatically resolve `course_name`/`course_color` from the course catalog (`_resolve_course` in `services.py`) when only `course_id` is given — both fields remain overridable for courses outside the catalog.

Four new entities mirror features that were recently added to the client but had no HA counterpart yet: `sensor.studylife_achievements_unlocked` (`_calc_achievements` in `coordinator.py`, 1:1 the same badge thresholds as `Index.razor`'s `BuildAchievementsAsync`, but deliberately over the same `SESSION_HISTORY_DAYS` window as the other sensors instead of its own ~10-year request — see the docstring there for the trade-off), `sensor.studylife_longest_streak` (`_calc_longest_streak`, longest streak ever achieved, independent of `sensor.studylife_streak`'s *current* streak), `sensor.studylife_topics_progress` (`_calc_topics_progress`, mirrors the topic checklist from `CourseGoalDto.completedTopics` against the catalog), and `binary_sensor.studylife_inactivity_warning` (mirrors `InactivityReminderService.cs`'s threshold logic exactly, including the special case "never had a session" → always on). The reminder thresholds (`sessionReminderMinutes`/`courseGoalReminderDays`/`inactivityThresholdDays`) and the new `recurrence_group_id` per session were additionally folded into `sensor.studylife_motivational_style`'s attributes and the session attribute helpers (`_session_attrs`/`_today_sessions_attrs`), without their own entity — purely extra info for automations, no separate state needed.

Two further sensors mirror the ECTS forecast and the month comparison: `sensor.studylife_study_forecast` (`_calc_forecast`, device class `date`, identical semester-based + pace-adjusted projection as `BuildForecast` in Stats.razor/Index.razor — see above —, attribute `recent_weekly_hours`) and `sensor.studylife_month_comparison` (`_calc_month_comparison`, hours in the current month plus `delta_vs_last_month_hours`/optional `delta_vs_last_year_hours`). Deliberately **no** separate long history requested for this — contrary to what might seem necessary at first, the already-loaded `SESSION_HISTORY_DAYS` window (~400 days) reliably always reaches back to the same calendar month of the previous year (worst case ~396 days); an additional 10-year request on every 30-second poll would have been unnecessary load. `_resolve_courses` (the basis for `selected_courses`/`completed_courses` on the `motivational_style` sensor) now additionally provides `tag` per course (from `CourseGoalDto.Tag`), and `sensor.studylife_notes` has a new `latest_session_id` attribute if the most recently edited note originated from the focus timer's reflection prompt.

Newly added: `calendar.studylife_course_goals` (a second calendar entity in `calendar.py`, all open course goals with `TargetDate` set as all-day entries — exclusive end date = target day + 1, as required by HA's all-day convention; description = `CourseGoalDto.Tag` if set) as well as `sensor.studylife_weekly_report` along with the bus event `studylife_weekly_report` (`_calc_weekly_report` in `coordinator.py`): state = the ISO week ID of the most recently completed Mon–Sun week, with hours/delta/top course/session count as attributes, so automations have a counterpart to the Sunday-6pm weekly-report push (`RunWeeklyReportAsync`, see above), which as a Web Push never reaches HA. The event only fires on an actual week change between two poll cycles of the same HA runtime — on the first refresh after a restart, the week ID is only remembered, otherwise every HA restart would trigger the report again.

It additionally offers four services — `studylife.create_session`/`update_session`/`delete_session` (using the same `POST`/`PUT`/`DELETE /api/sessions` endpoints as the calendar page; `update_session` merges unspecified fields against the last polled coordinator state, since the server always expects the full DTO) and `studylife.set_course_goal` (`PUT /api/coursegoals/{courseId}`, same merge behavior) — to manage sessions and course goals directly from automations. The config flow has a (mandatory since Phase 3) `api_key` field for one-time pairing — the user generates the long-lived per-user key on the app's Setup page (card "Home Assistant", see [Security](#security)) and enters it; it is sent as an `X-Api-Key` header. The key never rotates; a 401 (key regenerated/revoked in the app) triggers the reauth flow. The former `X-Api-Key-Rotated` adoption logic was removed along with the rotation mechanism. `api.py` also polls via conditional GET against the ETags of the server-side cached endpoints (`CacheHelper.cs`): the last `(ETag, body)` pair per request path is kept in memory, sent along via `If-None-Match`, and the cached body is reused on `304 Not Modified` — endpoints without an ETag behave unchanged. Details in the [integration's README](https://github.com/lukislp/studylife-hacs#readme). Remaining limitation: the free-text completion note is write-only (`set_course_goal`), not available for reading as a sensor; the study heatmap and the month/weekday/time-of-day charts on the evaluation page are deliberately not mapped as sensors (too data-heavy for attributes, pure visualization).

## studylife-ai integration (`Services/AiProxyTokenService.cs`, `Services/AiProxyClient.cs`, `Controllers/AiProxyController.cs`)

[studylife-ai](https://github.com/lukislp/studylife-ai) is a separate Python microservice (LangGraph agent + RAG over notes/courses/sessions) this backend proxies the Blazor chat component's requests to. The `AuthUserEntity.AiApiKeyHash` slot (`SettingsController`'s `ai-api-key` group, same one-time-plaintext/hash-only pattern as the Home Assistant key above) exists for `studylife-ai`'s own non-interactive ingestion worker - but a live browser session can't use it directly: this backend only ever stores the *hash*, never the plaintext, after generation, so it cannot forward a logged-in user's own key on their behalf (discovered while first implementing the live proxy - the original plan assumed it could).

Instead, `AiProxyController` (`api/ai/chat|agent|agent/confirm`, same `SessionUser`-only auth as the `ai-api-key` group - a bare API key must not be enough to drive the AI agent as someone else's session) mints a short-lived signed token per request via `AiProxyTokenService.Mint` (HMAC-SHA256 over `{userId}.{expiry}`, 5-minute lifetime, same base64url encoding style as `AuthSessionService.GenerateToken`) and forwards it as `X-StudyLife-Proxy-Token`. studylife-ai verifies the signature purely locally - no round-trip back here, and since the signature cryptographically binds `userId` to something only this backend can produce, verifying it also answers "does this really belong to this user" with no separate lookup needed. `AiProxyController` is a pure reverse proxy (`AiProxyClient.ProxyAsync`, `HttpCompletionOption.ResponseHeadersRead`) - request/response bodies pass through unparsed, including `/chat`'s SSE stream, so this backend never needs to know studylife-ai's request/response shapes.

For `/agent`'s real StudyLife API calls (`list_courses`, `create_session`, ...), studylife-ai still needs an actual, StudyLife-`X-Api-Key`-gate-accepted credential - the proxy token alone only proves identity, nothing else. `SettingsController.GenerateAiApiKey` therefore also calls `AiProxyClient.RegisterKeyAsync` at the one moment the plaintext exists (right after generation), handing it to studylife-ai's own persistent per-user registry; `RevokeAiApiKey` calls `RevokeKeyAsync` symmetrically. Both calls are best-effort (caught, logged as a warning, never thrown) - a studylife-ai outage must not fail StudyLife's own key generation/revocation, the user just can't use `/agent` or get their notes ingested until it's retried. Like APNs, the whole integration is gated on configuration (`StudyLifeAi:BaseUrl` plus a usable signing + internal-API secret, `AiProxyClient.Enabled`) and stays a silent no-op otherwise - `AiProxyController` returns `503` while unconfigured.

**Audit A5 (2026-08-26): split the one symmetric `StudyLifeAi:SharedSecret`** - it used to both sign every proxy token (so anyone holding it could mint a token for *any* `userId`) and authenticate `/internal/*` (register-key/revoke-key/enrich-capture), with no key-id, so rotating it meant a simultaneous redeploy of both services or a 401 window. Now two secrets, both set the same way as `SharedSecret` was (config/environment, e.g. `StudyLifeAi__TokenSigningSecret`/`StudyLifeAi__InternalApiSecret`):
- **`StudyLifeAi:TokenSigningSecret`** - one or more comma-separated `kid:secret` entries (e.g. `v1:abc...,v2:def...`); `AiProxyTokenService` always signs new tokens with the **first** entry, producing the new `{userId}.{expiry}.{kid}.{sig}` format (`AiProxyTokenService.Mint`, `ParseSigningKeys`). Rotate by prepending a new `v2:...` entry - studylife-ai (which accepts every kid still listed on its own side) keeps verifying old-`kid` tokens until they naturally expire (5 minutes), then the old entry can be dropped from both sides' config with no 401 window.
- **`StudyLifeAi:InternalApiSecret`** - the raw bearer sent as `X-StudyLife-Shared-Secret` to `/internal/*`; this side always sends the **first** comma-separated value if it's a list (`AiProxyClient.FirstCommaValue`) - studylife-ai's own `STUDYLIFE_INTERNAL_API_SECRET` is what actually holds multiple *accepted* values during a rotation.
- **Rollout compatibility**: when either new variable is unset, `AiProxyClient` falls back to the legacy `StudyLifeAi:SharedSecret` (`AiProxyTokenService.MintLegacy`, producing the original un-keyed 3-part token) and logs one deprecation warning - so this backend and studylife-ai can each deploy the split independently, in either order, without a coordinated cutover. See studylife-ai's `docs/decisions.md` ("Split the shared secret (audit A5)") for the verifier side of this contract.

**`/internal` port cutover, Phase A (2026-08-26):** studylife-ai's dual-port release serves `/internal/*` (`register-key`/`revoke-key`/`enrich-capture`) on its own port (`8001`) in addition to the public port (`8000`) that has always served `/chat`/`/agent`/`/agent/confirm`. This backend now has a second config key, `StudyLifeAi:InternalBaseUrl`, used for every `/internal/*` call (`RegisterKeyAsync`/`RevokeKeyAsync`/`EnrichCaptureAsync`, all via `AiProxyClient.PostInternalAsync`); `AiProxyController`'s public proxy (`ProxyAsync`) keeps using `StudyLifeAi:BaseUrl` unconditionally, unaffected by this change. **`InternalBaseUrl` falls back to `BaseUrl` when unset**, same as the audit-A5 secret split above - a single-port studylife-ai (self-hosters, `docker-compose.scale.yml`, or any deployment that hasn't rolled out the dual-port release yet) keeps working unchanged with only `BaseUrl` configured, no coordinated redeploy required. In the k8s manifests (`k8s/01-config-and-secret.yaml`'s `studylife-config` ConfigMap), prod now sets both `StudyLifeAi__BaseUrl=http://studylife-ai.studylife-ai.svc.cluster.local:8000` and `StudyLifeAi__InternalBaseUrl=http://studylife-ai.studylife-ai.svc.cluster.local:8001`; studylife-ai's own `k8s/` carries the matching `allow-studylife-to-internal-port` `NetworkPolicy` opening port 8001 to this backend. **Phase B** (a later, separate studylife-ai release that removes `/internal` from the public port 8000 entirely) can only ship once every deployment - prod included - has `InternalBaseUrl` actually set to the dedicated port; until then, `/internal/*` staying reachable on both ports is what makes this a safe, independently-deployable first step.

Full design rationale (including the two rejected alternatives - browser-held `AiApiKey`, and a parallel internal-service API instead of the registration push) lives in studylife-ai's own `docs/decisions.md`, "M4.5 Multi-user support" - kept there rather than duplicated here since that log is this project's own interview-prep decision record. Tests: `AiProxyTokenServiceTests` (including a golden-value test cross-checked byte-for-byte against an independent Python implementation of the same HMAC/base64url scheme, plus the new key-id format and `ParseSigningKeys` validation), `AiProxyClientTests` (HTTP request shape via a stub handler, same style as `ApnsPushTests.StubHttpHandler`, including the new-secret/legacy-fallback paths and, since Phase A of the `/internal` port cutover, that `ProxyAsync` keeps using `BaseUrl` while `RegisterKeyAsync`/`RevokeKeyAsync`/`EnrichCaptureAsync` use `InternalBaseUrl` when set and fall back to `BaseUrl` when it isn't), `AiProxyControllerTests` (401/503 gates - the actual proxy relay against a real studylife-ai instance is a manual live check, not automated here, same reasoning as APNs' real-Apple-delivery gap above).

## Performance optimizations (client & server)

Six targeted optimizations with no behavior change, implemented in the same pass:

1. **Granular state events instead of a single `OnChange`** (`AppStateService.cs`) — alongside the existing `OnChange`, `OnSessionsChanged`/`OnSettingsChanged` now fire individually, depending on which category changed during a poll or an explicit save/delete. `OnChange` remains unchanged (still fires for both categories) for consumers that don't need to distinguish.
2. **Throttled dashboard reload** (`Index.razor`) — `Index.razor` now subscribes specifically to `OnSessionsChanged`/`OnSettingsChanged` instead of the broad `OnChange`: a pure settings change (e.g. a theme switch) only reloads the lightweight fields and skips the ~10-year achievements/forecast/comparison fetch entirely; that only runs on actual session changes, additionally throttled to at most once per 5 minutes (`_lastHeavyFetchAt`/`HeavyFetchThrottle`) as a second safety net against several rapid successive session edits (e.g. several focus-timer sessions in a row).
3. **Server-side caching for `GET /api/sessions/history`** (`SessionsController.cs`) — `IMemoryCache`, cache key `history:{days}:{onlyCompleted}:{version}` with a 60s absolute TTL. `SessionHistoryCacheVersion` (a new singleton, `Services/SessionHistoryCacheVersion.cs`) is incremented after every `Create`/`Update`/`Delete`/`DeleteSeries`, which makes all previously cached entries unreachable for the next request (no active invalidation needed, they simply expire unused). **Important (bugfix):** browser-side, the data endpoints send `Cache-Control: private, no-cache` (revalidation via ETag/304), NOT `max-age` — a `max-age` let the browser answer the immediate refetch after a save from its own HTTP cache without ever asking the server, so the editing device only saw its own change after the TTL expired (symptom: calendar entry changed, view only updated after switching views). Only the runtime-immutable course catalog keeps a browser `max-age` (1h) — see `CacheHelper.GetOrSetAsync`'s `clientMaxAge` parameter.
4. **Splitting `Index.razor` into dashboard components** (`Components/Dashboard/*.razor`) — the previously ~1045-line monolithic page has shrunk to ~740 lines; 13 tiles (including `DashboardProgressCard`, `DashboardQuotaCard` — reused for both the weekly **and** monthly quota via a shared `QuotaCardData` record —, `DashboardTrendChart`, `DashboardAchievementsCard`, `DashboardMonthComparisonCard`) are now separate components that only receive already-computed values as `[Parameter]`. All calculation logic (`LoadDataAsync`, `BuildAchievements`, `BuildForecast`, `BuildMonthComparison`, `CalcStreak`) remains unchanged in `Index.razor` — pure markup extraction, no logic change. Resolved i18n strings are passed through as finished `string` parameters; the child components have no i18n text tables of their own.
5. **`app.css` split into topic-based files** (`wwwroot/css/`) — instead of a single 1784-line file, now 11 files (`base.css`, `shared.css`, `dashboard.css`, `stats.css`, `calendar.css`, `focus.css`, `setup.css`, `notes.css`, `planner.css`, `responsive.css`, `print.css`), linked in `index.html` in exactly the order that produced the original file's cascade (buttons/forms/modal were moved to `shared.css` in the process, since they're used across pages — before moving, it was checked that no selector appears more than once, to rule out cascade-order bugs). `planner.css` contains the existing Planner section unchanged, 1:1.
6. **Consolidated background services** (`Services/BackgroundTaskService.cs`) — see [Background services](#background-services-server) above: three independently polling `BackgroundService` instances (each with its own timer, its own DI scope per tick) were merged into one shared 30s tick loop, with each subtask keeping exactly its original interval via an internal "next-due" check.

**2026-09 latency pass (audit L1–L4, P1, P3, P4, Redis):**
- The blanket `/api` `Cache-Control: no-store` middleware only applies where the controller set no directive of its own. It used to overwrite `CacheHelper`'s `private, no-cache` + ETag, which forbade the browser from keeping the response at all — so no `If-None-Match` was ever sent and every 30 s poll and every dashboard navigation re-downloaded the full body. `no-cache` already forces revalidation on every use (the protection the native app's NSURLCache needed); heuristic caching only ever applies to responses without an explicit directive, and those still get `no-store`.
- `SessionHistoryCacheVersion` / `SettingsCacheVersion` are keyed per `AuthUserId` and fully async (`GetAsync`/`BumpAsync`). The old single process-wide (Redis-wide) integer meant any user's write invalidated every user's cache and ETag, and the facades read it via `GetAwaiter().GetResult()` on the request path — in Redis mode a blocked thread-pool thread per cache lookup. `IVersionCounter` takes a key; `RedisVersionCounter` stores `version:<prefix>:<userId>`, `InMemoryVersionCounter` a `ConcurrentDictionary`.
- Cache TTLs for `/api/sessions`, `/api/sessions/history`, `/api/settings` went from 15/60 s to 10 minutes. The key already changes on every write, so the TTL is a memory bound, not a freshness mechanism — at 15 s the entry had always expired before the 30 s client poll returned, so every poll paid the full query + serialization + cache write.
- Synthesized TTS audio moved out of `IDistributedCache` into `Services/TtsAudioCache.cs`, a per-pod `MemoryCache` with a hard `SizeLimit` (`Tts:CacheSizeMb`, default 32). Multi-megabyte WAV blobs with a 24 h TTL used to share the 96 MB `allkeys-lru` Redis with WebAuthn challenges, consent assertions and the DataProtection key ring (a few TTS calls could evict live login challenges), and on the single-instance/demo host the distributed cache is an unbounded in-process cache.
- Fonts are self-hosted (`wwwroot/fonts`, `@font-face` in `base.css`, OFL). The Google Fonts `@import` was invisible to the preload scanner and serialized two extra origins (DNS+TLS each) before first paint; the CSP no longer lists the Google hosts. `index.html` preloads the two latin faces every page uses and loads `print.css` with `media="print"`.
- The service worker precaches only the `de` and `en` i18n tables (plus everything else in the manifest except `.pdb`/`.map`); the full manifest was 655 assets including all 26 languages (416 JSON, ~1.7 MB raw) fetched during the WASM boot itself. Other languages load network-first when selected.
- Hot-path indexes (`AddHotPathIndexes` / `AddHotPathIndexesPostgres`): `Sessions(AuthUserId, StartTime)` replaces the single-column `StartTime` index, plus `Notes(AuthUserId, UpdatedAt)`, `Notes(AuthUserId, CourseId)`, `StudyPrograms(AuthUserId)`, `SessionTemplates(AuthUserId)`, `CustomCourses(AuthUserId)` — every read goes through the `AuthUserId` query filter, and none of these tables had a leading index on it.

## Security

Since Phase 3 of the multi-user overhaul, every `/api` request needs, at minimum, **either** a valid passkey session token (`X-Session-Token`, see Phase 2 below) **or** a per-user API key — enforced since audit finding A3 by a real ASP.NET Core `AuthenticationHandler` (`Auth/StudyLifeAuthenticationHandler.cs`, scheme `"StudyLife"`) plus a small set of authorization policies (`Auth/StudyLifeAuthorizationPolicies.cs`), registered via `app.UseAuthentication()`/`app.UseAuthorization()` in `Program.cs`. This replaced two hand-rolled inline middleware lambdas (~140 lines of path-string checks) that predated ASP.NET Core authentication being wired up at all; the credential resolution logic itself (which header/query param wins, in which priority, sliding session refresh) is unchanged, only where it lives moved. `ApiAccess` (any authenticated credential) is the `AuthorizationOptions.FallbackPolicy` — the default for every endpoint that states no requirement of its own; individual actions opt out via `[AllowAnonymous]` (the open `/api/auth` surface, the public progress-share link, `/api/system/version`) or tighten via `[Authorize(Policy = "SessionOnly")]` (a real session specifically, not a bare API key — see below) or the narrow `PublicUnlessInvalidSession` policy (reachable without any credential, but an `X-Session-Token` that IS present and invalid is still rejected — for the two GET endpoints above that are otherwise open).

- **Per-user API key (`AuthUserEntity.ApiKeyHash`):** a long-lived key exclusively for Home Assistant and similar non-interactive integrations that can't maintain a passkey session. Generated via `POST /api/settings/ha-api-key/generate` (Setup page, "Home Assistant" card; requires a real session): 32-byte CSPRNG, base64url — the plaintext leaves the server exactly once in the generate response; only the SHA-256 hash is stored (same pattern as `AuthSessions.TokenHash`, unique index). `StudyLifeAuthenticationHandler` matches the hash of the supplied `X-Api-Key` header (or `?apiKey=` query parameter) against `AuthUsers.ApiKeyHash`, thereby resolving authentication AND user identity in one step. **Deliberately no rotation, no expiry** (explicit user decision, "long lived"): Home Assistant has no live session that could react to a rotation — the former globally rotating key would have silently disabled the integration after any missed rotation (>10 days offline). Revocation via `POST /api/settings/ha-api-key/revoke` (hash is deleted, HA gets a 401 → reauth flow). The former `ApiKeyProvider` (global key in `app_data/api-key.json`, 30-day rotation, `X-Api-Key-Rotated` grace-window signal, `Security__ApiKey` pinning, bootstrap endpoint) has been completely removed.
- **Calendar token (`AuthUserEntity.CalendarToken`):** its own **permanently valid**, per-user token for exactly one route, `GET /api/sessions/ics` (the subscribable iCalendar feed). Reason: calendar apps (Google/Apple/Outlook) poll the feed URL on their own, can neither set custom headers nor go through a login. Lazily created on first fetch, no rotation; manually regeneratable via `POST /api/system/regenerate-calendar-token` (session-required). `StudyLifeAuthenticationHandler` resolves this route's owner from its own query parameter `?calendarToken=` (deliberately NOT `?apiKey=`, so the two secret spaces aren't interchangeable) — an EXCLUSIVE credential kind scoped to exactly this method+path, it never falls through to session/API-key resolution for that one route. The Setup page fetches the token for the subscription URL via the session-authenticated `GET /api/system/calendar-token`.
- **Browser client:** authenticates exclusively via its passkey session (`SessionHandler` attaches `X-Session-Token` to every request) — there is no `ApiKeyHandler`, no bootstrap round-trip, and no `ApiKey` seed in `wwwroot/appsettings.json` anymore. Even the Setup page's backup downloads now go through the HttpClient (blob download via `SetupBackupCard.razor.js`) instead of native `<a download>` links with `?apiKey=`.
- **Home Assistant:** one-time pairing via the (mandatory) API-key field in the config flow — generate the key on the Setup page, paste in the one-time plaintext shown. After that, no further intervention is ever needed; only a key regenerated/revoked in the app forces the standard reauth flow via 401. `StudyLifeConfigFlow.async_step_reconfigure`/`_confirm` (this is the only reason the "Reconfigure" entry even appears in the HA menu at all — HA does NOT show it automatically, unlike "Configure"/options flow) additionally lets both URL AND key be corrected together (e.g. a typo during initial setup, or a changed server address) instead of only the key like reauth; the URL serves as the `unique_id`, and a collision check only kicks in if it actually changes (otherwise the entry would be wrongly rejected as "already_configured" against itself).
- **studylife-ai:** a *separate* per-user key slot (`AiApiKeyHash`), same hash-only storage as the Home Assistant key, but not used the same way — a live browser session authenticates to studylife-ai via a short-lived HMAC-signed proxy token instead (`AiProxyTokenService`/`AiProxyController`), since this backend can't retrieve the plaintext key back out to forward it. Since the setup-page rework, the AI card is a plain on/off **toggle**: enabling calls `POST /api/settings/ai-api-key/generate` and the client *discards* the returned plaintext (studylife-ai receives it via the registration outbox, the user never needs it); disabling revokes. See [studylife-ai integration](#studylife-ai-integration-servicesaiproxytokenservicecs-servicesaiproxyclientcs-controllersaiproxycontrollercs) above for the full flow.
- **studylife-mcp:** its own per-user slot (`McpApiKeyHash`), provisioned without any user-visible key: the MCP server (HTTP mode, or the `studylife-mcp-login` CLI for stdio) sends the user's browser to `/connect/mcp` (passkey login + consent, the shared `ConnectConsent` component), and the resulting assertion is redeemed server-to-server for a freshly rotated key — see the consent-assertion mechanism below. The Setup page offers no MCP key at all anymore.
- **studylife-capture:** same mechanism with the `capture` audience (`CaptureApiKeyHash`, `/connect/capture`), initiated by the Chrome extension via `chrome.identity.launchWebAuthFlow`; the exchanged key lives only in the extension's `chrome.storage.local`.

**Consent-assertion mechanism (audience-parameterized, `AuthController`):** both connect flows share one implementation. The consent page's session-authenticated `POST /api/auth/{mcp|capture}-connect` validates the caller-supplied `redirectUri` against a per-audience allowlist (the extension's `https://<id>.chromiumapp.org/` callback for `capture`; an RFC 8252 loopback exception — `http://127.0.0.1`/`localhost`, any port — for the stdio login CLI), **rotates** the slot's key, and caches a `PendingConsentAssertion(UserId, Audience, ApiKey)` under a CSPRNG assertion value with a 120s lifetime. The anonymous `POST /api/auth/{mcp|capture}-assertion-exchange` redeems it **exactly once**; a wrong-audience redemption answers 401 *without* consuming the assertion, so probing the capture exchange can't burn a pending MCP assertion (or vice versa). Because re-running the consent flow simply rotates the key again, "rotation" needs no UI of its own; emergency disconnect per slot lives on the Setup page's "External connections" card (`SetupExternalConnectionsCard.razor`).

**Security model:** unlike the former global key (which was retrievable by anyone who could load the page via the unprotected bootstrap endpoint), there is now no API secret that the server hands out unauthenticated: session tokens only arise from a real passkey login, API keys only from a logged-in session. A leaked per-user key compromises exactly one account and can be revoked immediately via the Setup page — the lifetime cap via rotation is deliberately dropped in exchange (a trade-off in favor of an HA pairing that never silently breaks).

**Per-slot endpoint scoping (audit finding A6 round 2):** the four key slots above existed only for independent *rotation* — until this change, any one of them, once authenticated, reached the FULL `/api` surface (any note/session/course-goal/setting, of every kind). A leaked `capture` key (sitting in a browser extension's storage, the least-trusted of the four) could therefore read and delete everything the account owns, not just create notes. `Auth/ApiKeyScopes.cs` now holds ONE explicit map of `slot -> allowed (Controller, Action)` pairs, inventoried from each real consumer's actual client code (`studylife-hacs/custom_components/studylife/api.py` + `services.py`, `studylife-mcp/src/studylife_mcp/client.py`, `studylife-ai/src/studylife_ai/studylife/client.py`, `studylife-capture/src/api.ts`) rather than from what an integration theoretically might want — `ha` is by far the widest slot (it also drives the calendar and settings on the user's behalf via six `studylife.*` HA services), `capture` the narrowest (`GET`/`POST /api/notes` only). `GET /api/auth/whoami` is allowed for every slot (identity contract v1 §1). Session and calendar-token credentials are untouched — both keep unconditional full access, same as before (a session already IS the logged-in user; the calendar token can by construction never reach anything but `GET /api/sessions/ics`).

Enforced by `Auth/ApiKeyScopeAuthorizationHandler.cs`, an `IAuthorizationHandler` for a new `ApiKeyScopeRequirement` added to the `ApiAccess` policy (the same policy that is also `AuthorizationOptions.FallbackPolicy`, so both are covered — `SessionOnly`/`PublicUnlessInvalidSession` do not carry this requirement and are therefore unaffected by any of this). A request outside its slot's scope gets **403 Forbidden**, not the usual 401 — deliberately different from every other rejection this auth stack answers with 401 (see `StudyLifeAuthorizationPolicies`): the credential itself is genuinely valid, it's just not permitted to do *this*, which is exactly the case `AlwaysChallengeAuthorizationMiddlewareResultHandler` now carves out as an explicit exception (only when the *sole* failed requirement is `ApiKeyScopeRequirement` — any other simultaneous failure, e.g. no credential at all, still gets the usual blanket 401).

Rollout escape hatch: `Security:EnforceKeyScopes` (`appsettings.json`, default `true`). Set to `false` for log-only mode — every would-be-denied request is still let through, but logged as a `Warning` (`API key slot {Slot} would be DENIED access to {Endpoint} …`) so the matrix can be validated against real production traffic (HA polling, the MCP server, studylife-ai's ingestion worker, the capture extension) before it starts actually rejecting anything.

**Consent redirect allow-list (2026-09 audit S1):** the five hardcoded consent audiences (`AuthController.5.Consent.cs`: mcp, capture, focusguard, focustunes, tray) used to accept ANY absolute https `redirect_uri`. Their `*-assertion-exchange` endpoints are anonymous and take nothing but the single-use assertion, so whoever received the browser redirect could redeem it for the freshly rotated key — `/connect/mcp?redirect_uri=https://attacker.example/cb` was a one-click key theft. `Services/ConsentRedirectPolicy.cs` now decides per audience: mcp/tray accept the RFC 8252 loopback shape plus exact URIs listed under `Consent:AllowedRedirectUris:<audience>` (the HTTP-mode studylife-mcp server's `/auth/studylife/callback` goes there — `k8s/01-config-and-secret.yaml`); the three browser-extension audiences accept `https://<extension-id>.chromiumapp.org/...` (`chrome.identity.getRedirectURL()`) plus configured URIs; anything else is a 400 and the key slot is left untouched. `AuthController.IsAllowedRedirectUri` stays as the shared syntactic first stage (also used by `DeveloperController` for registered OAuth-client URIs, which `AuthController.10.OAuthClients.cs` already matched exactly). The consent card (`Components/ConnectConsent.razor`) additionally shows the redirect target's host, so the human sees where the hand-off goes before clicking Connect.

## Security review after Phase 3 (eight findings, all fixed)

After the complete multi-user overhaul, a targeted security check turned up four gaps, plus a fifth bug found functionally (not via security review, but live while creating a second real account), plus three more from a second review round — all traceable to the same root cause: code that predates the multi-tenant conversion and was overlooked during it. All eight are fixed, with regression tests that set up a real two-user situation via the passkey registration flow (not just single-user mocks):

- **Push notifications crashed for the second user in the same browser (`SqliteException`, `UNIQUE constraint failed: PushSubscriptions.Endpoint`):** `PushSubscriptionEntity.Endpoint` was deliberately GLOBALLY unique ("a push endpoint belongs to exactly one browser profile") — true only as long as one browser profile also had only one app user. The Push API returns the same endpoint for the same origin, regardless of which StudyLife account is currently logged in; when a second user in the same browser signs up for push, `PushController.Subscribe` attempts an INSERT with the same endpoint but a different AuthUserId — the collision (invisible due to the query filter) with the first user's row violated the global uniqueness. Fix: a unique index on `{AuthUserId, Endpoint}` instead of `Endpoint` alone (same pattern as `CourseGoals`/`SentReminders`) — both users now get their own subscription row for the same physical endpoint and thus their own push notifications on the same device, independently of each other.

- **Backup/restore bypassed the entire user separation (`BackupController.cs`):** `GET /api/backup/database`, `.../database/encrypted`, `POST /api/backup/restore` (+ `restore/status`, `restore/cancel`, `restore/restart`) operate on the RAW SQLite file (`DatabaseBackupService`/`DatabaseRestoreService`), not via the filtered EF queries like the rest of the app — any logged-in user (even a freshly self-registered second account) could thereby download or replace the database of ALL users. Fix: `BackupController.IsOwnerAsync()` restricts these six endpoints to the first-registered user (the installation's owner) AND requires a real session (no API key) — `GET /api/backup/export` deliberately stays open to every user, since it goes through the normal query filters and only returns that user's own data anyway. A gotcha along the way, observed live: `Unauthorized()` (401) gets misinterpreted by the client (`SessionHandler.cs`) as "session dead, log out" — a second user got kicked out just from opening the Setup page (which polls `restore/status` in the background), even though their session was perfectly valid, they simply weren't the owner. Fix: `IsOwnerAsync()` calls `Forbid()` (403), not `Unauthorized()`; `SessionHandler.cs` only reacts to 401, not 403. (Historical note: before audit finding A3 introduced a real `AuthenticationHandler`, `Forbid()` crashed with an `InvalidOperationException` — no ASP.NET Core authentication scheme was registered at the time, auth ran entirely through custom middleware — so this endpoint set the status code directly via `StatusCode(403)` instead; now that a scheme exists, it calls `Forbid()` like normal, with byte-identical output. This is also why `IsOwnerAsync()` stays a manual check rather than `[Authorize(Policy = "SessionOnly")]`: that policy always answers a rejection with a 401 challenge — see `Auth/StudyLifeAuthorizationPolicies.cs` — which is exactly the response this endpoint must NOT give to a logged-in-but-not-owner request.)

  UX follow-up: instead of letting a non-owner click an unusable backup/restore UI that then fails with 403, the client hides it outright. `GET /api/auth/account-info` (`AuthController.GetAccountInfo`, session-required) returns `AccountInfoDto.IsOwner` — deliberately its own DTO instead of a field on `UserSettingsDto`, since it's not a user setting and would otherwise have to go through `ComputeSettingsHash`. `AppStateService.GetIsOwnerAsync()` caches this (one fetch per page-visit session, analogous to `GetSettingsAsync`). `Setup.razor` hides `SetupRestoreCard` entirely and lets `SetupBackupCard` show only the (valid-for-every-user) JSON export, not the raw `.db` download. `Index.razor` suppresses the backup-staleness dashboard hint for non-owners — it would otherwise stay lit permanently, since `UserSettings.LastBackupDownloadAt` can never be set for them (only the now owner-only downloads set it).
- **The ICS calendar feed showed every user the first account's calendar:** the former `CalendarTokenProvider` was a single, process-wide token for ALL users; combined with the "no header → Phase-1 fallback to first AuthUser" behavior of the gate middleware, EVERY caller always only got the first-registered user's calendar. Fix: `AuthUserEntity.CalendarToken` (plaintext, lazily created on the first `GET /api/system/calendar-token`, session-required) completely replaces the global provider; the ICS gate exception in `Program.cs` now resolves the actual owner through it (analogous to the per-user API key) instead of only validating. `CalendarTokenProvider` including its tests was fully removed.
- **The progress share link was broken for everyone except the first user (404 despite a valid own token):** `ProgressController.GetShared` loaded the settings row via the ambiently resolved (always first) user instead of looking up the real owner by the token. Fix: `_db.Settings.IgnoreQueryFilters().FirstOrDefaultAsync(s => s.ProgressShareToken == token && s.ProgressShareEnabled)` searches token-based across ALL users (the 32-byte CSPRNG token itself is the authorization here), followed by `CurrentUserAccessor.BeginBackgroundScope(settings.AuthUserId)` for the rest of the method, so CourseGoals/StudyProgramCatalog scope correctly as well.
- **Rate limiter bypassable via X-Forwarded-For spoofing:** `ForwardedHeadersOptions.KnownIPNetworks`/`KnownProxies` were completely empty (trusts ANY sender), and `docker-compose.yml` publishes port 8080 on all host interfaces (no static Docker bridge subnet can be pinned, because the same Pi runs several independent Compose stacks including a shared nginx-proxy-manager instance) — anyone reaching the port directly instead of via nginx could arbitrarily bypass the IP-partitioned rate limiter. Fix: `KnownIPNetworks` restricted to private/RFC1918 ranges (covers both Docker bridge subnets and the LAN that nginx actually connects through, neither statically predictable). Deliberately NOT fixed: binding port 8080 itself as non-public, because that would affect the shared nginx infrastructure for other services on the same host — an attacker from a private address range could therefore theoretically still exploit the gap.
- **`IMemoryCache` keys of `SettingsController`/`SessionsController` were global instead of per user — a real cross-user data leak, not just an inefficiency as originally assumed (see the Phase-1 section above):** `GET /api/settings` (`settings:{version}`), `GET /api/sessions` (`sessions:all:{version}`), and `GET /api/sessions/history` (`history:{days}:{onlyCompleted}:{version}`) cached under a key made up only of the global version counter — `SettingsCacheVersion`/`SessionHistoryCacheVersion` are singletons, `IMemoryCache` is shared process-wide. If user A calls the endpoint and user B calls the same endpoint within the TTL window (15s for settings/sessions, 60s for history, both sized around the 30s client poll) WITHOUT anyone having written in between, B gets A's complete response body including `ProgressShareToken`/notes/course history — the `cache.TryGetValue(key, ...)` hit in `CacheHelper.GetOrSetAsync` knows no user, only the key. Fix: `_currentUser.AuthUserId` woven into each of the three cache keys (and thereby automatically into the ETag, since the key serves 1:1 as the ETag) — `SettingsController`/`SessionsController` needed `ICurrentUserAccessor` as a new constructor dependency for this. `CoursesController`'s `courses:program:{id}` key deliberately stays unchanged: the preceding `AnyAsync` check already goes through the query filter, a foreign `id` falls back to the built-in catalog before the cache is even hit.
- **Whoever reached the open registration first automatically became the installation's "owner":** `RegisterComplete` claims, on the very first passkey registration ever (`!PasskeyCredentials.AnyAsync()`), the legacy user created by the Phase-1 migration along with all its existing data — and owner status (lowest `AuthUsers.Id`, see `BackupController.IsOwnerAsync`/`AuthController.GetAccountInfo`) comes with exclusive backup/restore rights over the RAW database. Since port 8080 is published on all host interfaces (shared nginx-proxy-manager infrastructure, see above), on a fresh/just-migrated installation anyone on the LAN could theoretically have claimed this role before the actual operator. Fix: a new `SetupSecretService` (`app_data/setup-secret.txt`, same persistence/read pattern as `VapidKeyProvider` including `SecretFileReader`) generates, on every startup as long as no passkey exists yet, an 8-character code (`LinkCodeAlphabet` format, `XXXX-XXXX`) and writes it prominently to the console (`docker logs`/`docker compose logs`). `AuthController.RegisterBegin` requires this code (via `CryptographicOperations.FixedTimeEquals`) ONLY for the very first registration — every further one (a family member joining) stays as fully open as before. After a successful first registration, `Program.cs` deletes the file again (never needed again); as long as unclaimed, the code is re-emitted on every restart, in case the operator missed it on first boot. On the test side this required an adjustment to 22 call sites of the shared `PasskeyHttp.RegisterAsync` helper (each test class starts with an empty temp DB, so every "first" registration in it now also needs a code — isolated for tests via `CustomWebApplicationFactory.SetupSecretDir`) plus rerouting the `SetupSecretService` registration to a temp directory per factory instance (analogous to `DatabaseBackupService`/`DatabaseRestoreService`), otherwise parallel-running test classes would have torn the code away from each other via `Clear()`.
- **`POST /api/auth/login/begin` revealed the credential IDs of ALL registered users to anonymous callers:** `AllowedCredentials` in the WebAuthn assertion options was populated with all `PasskeyCredentials.CredentialId` from the DB, regardless of who's asking — every anonymous call to the unauthenticated login endpoint (an auth exception in the API-key gate) thereby exposed the user count and handed out every opaque credential handle. Unnecessary, because registration with `ResidentKey = ResidentKeyRequirement.Required` produces discoverable credentials — the browser/authenticator finds the passkeys matching the RP ID itself in the OS store, with no hint list at all (that's exactly what enables the usernameless login screen). Fix: `AllowedCredentials` stays an empty list, no functional change to the login flow.

## Typical pitfalls when making changes

- Changing a DTO in `StudyLife.Shared` **without** adjusting the corresponding entity/mapping in the controller **and** `AppStateService` silently breaks serialization (fields simply come out `null`/default).
- `SelectedCourseIds`/`CompletedCourseIds` remain comma-separated strings in the DB — when extending this (e.g. beyond int IDs), touch the migration plus both `ToDto`/Save methods in `SettingsController`.
- Course catalog changes now happen in `StudyLife.Shared/CourseCatalog.cs` (no longer `Client/Models/Models.cs`) — still has **no** effect on already-saved sessions/course goals (they froze `CourseName`/`CourseColor` at creation time), but is now also known to the HA integration via `/api/courses`.
- New dashboard fields (`Index.razor`) are still computed client-side too (offline capability) via `StudyLife.Shared/StudyMetrics.cs`/`AchievementCatalog.cs` — but as of the Metrics API (`MetricsController`, see above), a new derived metric should get its own `StudyMetrics`/`AchievementCatalog` function AND a `MetricsSummaryDto`/`MetricsAchievementsDto` field, not just an inline client computation, or non-.NET consumers (HA, ...) are back to re-implementing it themselves.
- Validation in `SessionsController`/`CourseGoalsController` is deliberately minimal (no data annotations/FluentValidation, just a few manual `if` checks matching the codebase's otherwise lean style) — anyone needing further invariants extends the respective controller's private `Validate(...)` method, not a central validation framework.
- `TimerStateEntity` is deliberately "best effort": the client only pushes on state transitions, not guaranteed (e.g. on a browser crash, the last reported state stays as-is, even if the timer has long since stopped). Not a problem for consumers, as long as they check `PhaseEndsAt` against the current time instead of blindly trusting `IsRunning`.
- The per-user API key (see [Security](#security)) is stored ONLY as a SHA-256 hash — there is no server-side way to recover the plaintext. "Key forgotten/lost" always means: regenerate on the Setup page and give Home Assistant the new value (reauth dialog). The browser client is never affected by this (pure session auth).
- JS interop from lifecycle methods (`OnInitializedAsync`/`OnAfterRenderAsync`) **always** needs a try/catch wrapper: an installed PWA client may still serve an `index.html` cached by the old service worker that simply doesn't know a newly added JS helper — the interop call then throws and Blazor shows the error banner (this happened with `initCalendarSwipe` on the Calendar page). Missing helpers must degrade silently (the feature is just missing), never crash the page.

## Study report / PDF export (`Pages/Report.razor`, route `/report`)

A printable, human-readable study record (total hours, hours per course, ECTS progress incl. average grade, course target status, reporting period + creation date) — deliberately separate from the raw `.db` backup (`BackupController`/`DatabaseBackupService`): the report is meant for humans (scholarship application, study advisor), the backup for technical restoration. No new PDF package (no QuestPDF/iText, no jsPDF) — same principle as the calendar weekly print above: a dedicated, print-optimized page plus `window.print()` via the already-existing `printPage()` interop (`index.html`), no new JS code needed. The report computes the same formulas as `Stats.razor.cs` (weighted average grade via `StudyMetrics.CalcWeightedAverageGrade`, ECTS via `CourseCatalog.CalcTotalEcts`/`CalcEctsEarned`), but fetches the session history itself via `api/sessions/history?days=3650` instead of via `AppStateService.GetSessionsAsync` (±7/90-day window) or Stats' own 371-day window — a record of "the entire study period so far" needs more than a one-year look-back. A new `@media print` block in `print.css` (via a `:has()` selector on `.main-content:has(.report-page)`, without `MainLayout.razor` needing its own shell class for the route) makes only `.report-page` printable and forces black-on-white instead of the dark-theme variables. Entry point: a button on `Stats.razor`, extracted into `Components/Stats/ReportExportLink.razor` (its own `OnInitializedAsync`, its own `ReportText` i18n table) instead of a new field in `Stats.razor.cs` — reduces collision surface with parallel work on that file.

## Session templates / quick-add (`SessionTemplatesController.cs`, `Pages/Calendar.SessionTemplates.razor.cs`, migration `AddSessionTemplates`)

One-click creation of recurring sessions (e.g. "Analysis lecture, 90 min, Mondays 10:00"), without retyping course/duration/topic every time. Persisted server-side (`SessionTemplateEntity`: name, CourseId/-Name/-Color denormalized like on `StudySessionEntity`, DurationMinutes, optional topic, optional DefaultWeekday+DefaultStartTime) instead of localStorage — unlike, say, the ambient-sound feature, templates are deliberately chosen data that would be annoying for the user to lose, not a pure device-preference cache. `SessionTemplatesController` only offers list/create/delete (no update) — delete + recreate is enough for this simple feature.

Client-side, its own partial-class file `Calendar.SessionTemplates.razor.cs` instead of extending `Calendar.SessionDialog.razor.cs` — the same collision avoidance as with the concurrently landed ICS import (`Calendar.ImportIcs.razor.cs`), but it directly accesses that file's private form fields (`_formCourseId`, `_formStart`, ...), since partial classes share field visibility across files. Two directions of interaction:

- **Template → session:** a "From template" dropdown at the very top of the session modal (only for new sessions, only when templates exist) takes over course/topic/duration from the chosen template. The **day** the user clicked in the calendar is preserved — only the time is set to the template's `DefaultStartTime` (if present), everything remains normally editable afterward. `DefaultWeekday` is a pure display aid in the template list, not enforced when applying (a deliberate MVP decision: the user already clicks a day in the calendar anyway).
- **Session → template:** a "Save as template" toggle in the session modal (visible for both new and existing sessions' forms alike) takes over the current form values including `DefaultWeekday`/`DefaultStartTime` automatically from `_formStart` — no separate weekday/time selection needed.

A separate management modal (button next to the ICS-import button, same `.modal-overlay`/`.modal`/`.modal-footer` pattern) shows the saved templates with two-step delete confirmation (inline yes/no per row, same pattern as `_confirmingDelete` in the session modal) — no edit function, only list + delete.

## Read-only progress link (`ProgressController.cs`, `Pages/SharedProgress.razor`, route `/shared/{token}`)

A public link reachable without login/API key (`GET /api/progress/shared/{token}`) that shows a compact progress snapshot (total/earned ECTS, ECTS-weighted grade average, active courses with topic progress) — for sharing with parents, a mentor, or student advising. Deliberately NO access to notes, session details, or settings; `ProgressShareDto` is its own, minimal DTO instead of exposing `CourseDto`/`CourseGoalDto` directly.

Unlike the permanent ICS calendar token (`CalendarTokenProvider`, an in-memory singleton file), the token lives directly in `UserSettingsEntity.ProgressShareToken` + `ProgressShareEnabled` (bool) — deliberately its **own** token space, not reusing the calendar token: semantically separate (appointments vs. progress snapshot) and independently regeneratable. Enable/disable/regenerate go through their own `POST /api/settings/progress-share/{enable,disable,regenerate}` endpoints instead of the normal `PUT /api/settings` — same reasoning as with `LastBackupDownloadAt` (a dedicated write path): enabling must atomically generate a cryptographically strong token (`RandomNumberGenerator`, same technique as `CalendarTokenProvider`); a client round-trip via the generic PUT could otherwise save a half-enabled state. Disabling keeps the token (no need to re-share the URL if the user only temporarily switches the link off); only an explicit regenerate invalidates it.

`Program.cs`'s API-key gate has a third exception for this (after the bootstrap key and the ICS feed): `GET /api/progress/shared/*` with a non-empty path remainder is let through; the actual token check happens in the controller itself (needs DB access, unlike the in-memory singleton comparison for the ICS token) and responds with 404 instead of 401/403 for an invalid/missing/disabled token (doesn't even reveal to a scanner whether the path exists).

Client-side, a dedicated, deliberately navigation-less `Shared/PublicLayout.razor` (no `MainLayout`) for `Pages/SharedProgress.razor` (`@layout` override) — prevents an anonymous viewer from stumbling, via the normal app sidebar, onto other, non-shared data. Its own i18n table `ProgressShareText` (instead of handing the page other pages' tables) plus additional keys in the existing `SetupText` table for the Setup card. The Setup card itself (`Components/Setup/SetupProgressShareCard.razor`) is, like `SetupRestoreCard`, a self-contained component with its own HTTP access instead of a parameter bundle in `Setup.razor` — reduces the change to `Setup.razor`, which several feature batches share, to a single inclusion line.

## Multi-tenant foundation, Phase 1 (`Data/StudyLifeDb.cs`, `Services/CurrentUserAccessor.cs`, migration `AddMultiTenantAuthUserFoundation`)

StudyLife was a single-user app; the conversion to "several people with their own accounts" happens in three phases. Phase 1 (implemented) is ONLY the data-model foundation: a new table `AuthUsers` (`AuthUserEntity`: Id, DisplayName, CreatedAt) and a mandatory `AuthUserId` field on all twelve user-related tables (Sessions, Settings, PushSubscriptions, SentReminders, Notes, CourseGoals, TimerState, StudyPrograms, CourseGroups, CustomCourses, SessionTemplates, CourseResources) — deliberately without an FK constraint, the same loose pattern as `CourseId`. `UserSettingsEntity` is thereby no longer a singleton row, but one row per user. Phase 2 brings passkey/WebAuthn login and real registration, Phase 3 per-user API keys for Home Assistant.

**Filtering via EF global query filters instead of controller changes:** `StudyLifeDb.OnModelCreating` registers `HasQueryFilter(e => e.AuthUserId == _currentUser.AuthUserId)` for each of the twelve tables; the `ICurrentUserAccessor` is injected into the DbContext constructor, and the field access in the filter expression is re-evaluated by EF as a parameter on every query execution. This makes every existing LINQ query automatically user-specific without any controller having to be touched — in particular, the tabooed `PlannerController` keeps working unchanged and is nonetheless correctly filtered. Symmetrically, a `SaveChanges`/`SaveChangesAsync` override (`StampAuthUserIdOnAddedEntries`) automatically stamps every newly inserted row with `AuthUserId == 0` onto the current user — centralized instead of at every individual `.Add` call site, for the same reason (the insert site in PlannerController must not be edited). Consequence: `AddDbContext` instead of `AddDbContextPool` in `Program.cs`, because pooled contexts only allow a plain `DbContextOptions` constructor; with 1–2 users on the Pi this is irrelevant.

**"Current user" resolution (`ICurrentUserAccessor`/`CurrentUserAccessor`):** deliberately NOT a header sent by the client (would be trivially spoofable). For HTTP requests, a middleware in `Program.cs` that runs AFTER the existing API-key gate sets `HttpContext.Items["AuthUserId"]` to the id of the one existing `AuthUserEntity` (`FirstOrDefaultAsync` — in Phase 1 there can't be a second one, since there's no registration); authorization remains exactly as strong as before. This also applies to the token exception paths (ICS feed, progress share): there too, "the one user" is the correct resolution, otherwise these endpoints would see only empty data through the filters. For background work without an HTTP request, `CurrentUserAccessor.BeginBackgroundScope(id)` provides an `AsyncLocal` scope; priority in the accessor: AsyncLocal scope > HttpContext.Items > (tests only) static fallback > 0. 0 never matches, since real ids start at 1.

**BackgroundTaskService:** `ExecuteAsync` iterates, per tick, over all `AuthUsers` rows on the outside and runs the unchanged check logic per user in its own DI scope + `BeginBackgroundScope`; user-independent tasks (VACUUM, weekly backup dump) run exactly once per tick outside the loop (the former API-key rotation check has gone away with Phase 3). The sent-memos (`_weeklyReportSentForWeek` etc.) are now dictionaries keyed by AuthUserId.

**Migration/backfill:** `AddMultiTenantAuthUserFoundation` creates exactly ONE `AuthUser` ("My studies") via `migrationBuilder.Sql` and sets the `AuthUserId` of all existing rows to its id — existing data stays exactly the same for today's user. On fresh DBs (tests, new installation) the UPDATEs are no-ops, the user exists nonetheless; the test factory relies precisely on that (fallback id 1). The formerly global unique indexes `CourseGoals.CourseId`, `SentReminders.Key`, AND (since a follow-up fix, see the security-review section below) `PushSubscriptions.Endpoint` are now composite-unique with `AuthUserId` (otherwise users would block each other). `AuthUserId` deliberately does NOT appear in any DTO (no settings sync layer, no `ComputeSettingsHash`) — it's server-internal tenancy metadata, not a setting.

Known items deliberately deferred to Phase 2/3: `SettingsCacheVersion`/`SessionHistoryCacheVersion` remain global counters (with multiple users they invalidate too often, never too little — the invalidation timing is uncritical); the cache KEYS derived from them were not — see the security-review section below, since the fix every key additionally carries the `AuthUserId`. The progress-share/ICS token only gets its own user assignment in Phase 2/3; `BackupController.Export` through the filters now exports only the current user's data (in Phase 1 identical to before).

## Passkey/WebAuthn login, Phase 2 (`Controllers/AuthController.{1.Registration,3.Login,6.Identity,9.Devices}.cs`, `Services/AuthSessionService.cs`, migration `AddPasskeyAuth`)

Phase 2 puts the "door" on top of the Phase-1 foundation: registration and login via passkey (WebAuthn, Fido2NetLib 4.x — the cryptography/attestation verification comes entirely from the library, none of it is homegrown). Two new tables without a query filter (login necessarily runs BEFORE user resolution): `PasskeyCredentials` (CredentialId unique, COSE public key, SignCount as replay protection, freely editable DeviceLabel) and `AuthSessions` (`TokenHash` = SHA-256 of the plaintext token, which leaves the server exactly once; unique index).

**Registration case distinction (`AuthController.RegisterComplete`):** the very first registration ever (no passkey in the DB yet) "claims" the legacy user created by the Phase-1 migration — only its `DisplayName` is updated to the input, all existing data stays assigned to the registering human. Once at least one passkey exists, every further registration creates a brand-new, empty user (open signup for family members, intentional). The decision deliberately happens only in `complete` (not `begin`), in a transaction: aborted registrations thus never leave orphaned users, and two simultaneous first registrations can't both claim the legacy user. Registration issues a session directly (the attestation proof is the same as at login); the session-required additional-passkey path (`register/begin-additional`) attaches further devices to the same user and does NOT issue a new session. The WebAuthn user handle is an opaque random handle only for the browser dialog — account association runs exclusively via the unique CredentialId, so it isn't persisted.

**Sessions (`AuthSessionService`):** a 32-byte CSPRNG token (base64url), sliding extension `ExpiresAt = now + 90 days` on every valid request, hard-capped at `HardExpiresAt = IssuedAt + 180 days` — so even daily use forces a fresh passkey login at least every six months. `login/complete` opportunistically cleans up expired sessions (no dedicated background job).

**Credential resolution (`Auth/StudyLifeAuthenticationHandler.cs`, since audit finding A3):** almost every `/api/auth` action is `[AllowAnonymous]` (login/registration need no upfront credential); session-required auth endpoints are guarded by `[Authorize(Policy = "SessionOnly")]` or, where the requirement is conditional (`RegisterComplete`), by reading `HttpContext.SessionAuthUserId()` directly — both ultimately read `HttpContext.Items[AuthSessionService.SessionItemKey]`, set ONLY after real token validation, exactly as before. User resolution priority (unchanged since Phase 3, only where it lives moved): (1) a valid session token → its user, including sliding refresh; a SUPPLIED but invalid token ALWAYS fails authentication, even alongside a valid API key — a silent fallback would show the wrong user's data, and the explicit 401 is the only signal the client can act on to discard its token; (2) per-user API key → the user the key hash belongs to. There is no "first `AuthUser`" fallback for a request with no credential at all (removed as audit finding A2) — `CurrentUserAccessor.AuthUserId` stays 0 (its documented "no user resolved" value) and the EF global query filters simply return no data.

**Client:** `SessionTokenStore` (token in localStorage, loaded once before `RunAsync`) + `SessionHandler` (`DelegatingHandler`, attaches `X-Session-Token`; since Phase 3 the client's only auth handler). "No pointless logout", literally: the token is discarded ONLY on an explicit 401 response to a non-`/api/auth` request (then a redirect to `/login` via a `MainLayout` event) — never on network errors/timeouts, and `/api/auth` 401s (a failed login attempt) don't touch it; this also applies with no token attached at all (no login state present), otherwise the app would be stuck on a broken page with no error handling whatsoever. **Route protection:** `MainLayout` (the `DefaultLayout` of all pages except `/login`/`/register`/`/shared/{token}`, which explicitly set `PublicLayout`) checks `TokenStore.Token` synchronously as the VERY FIRST line in `OnInitializedAsync` (before any `await`, since the token is already loaded before `RunAsync`) and renders `@Body` only behind `@if (_authenticated)` — if the token is missing, the routed page (e.g. `Stats.razor`/evaluation) is never even instantiated, no data fetch of its own starts, nothing becomes visible before the `forceLoad` redirect to `/login` kicks in. A locally present but server-side invalid/expired token remains a (due to the 401 race, unavoidable) special case, handled reactively via `SessionHandler`/`OnSessionInvalidated` — the client never sees the actual data in this case, since the server gate refuses it either way. The `/login`/`/register` pages run in `PublicLayout` with the progress-share styles; the collocated JS module `Pages/Login.razor.js` (base64url↔ArrayBuffer glue around `navigator.credentials`) is shared and imported by Login, Register, AND `PasskeyDeviceManager` (the fourth fab-action in the MainLayout speed dial: list/rename/remove/additional passkey/logout; the last passkey can't be deleted = self-lockout protection). After login/registration, `NavigateTo("/", forceLoad: true)`, so `AppStateService` doesn't keep showing another account's caches. Fido2 RP-id/origin are derived per request from host/scheme (correctly, behind nginx, via `UseForwardedHeaders`), overridable via `Fido2:ServerDomain`/`Fido2:Origins`.

**Approval workflow for additional passkeys (`PasskeyCredentialEntity.ApprovedAt`):** a passkey created via `register/begin-additional` OR `register/begin-linked` is NEVER immediately usable (`ApprovedAt = null`) — an already-logged-in device must first explicitly approve it via the device list (`PasskeyDeviceManager`, `POST credentials/{id}/approve`). Rationale: a stolen/reused session token alone must never be enough to permanently slip in a second, independent means of access — the signature at registration proves possession of the new authenticator, but not that the account holder actually wanted it. In this state, `LoginComplete` deliberately returns not a generic 401 but `{"error":"pending_approval"}` (no additional information leak, since the signature has already been validated as genuine). The "last passkey" self-lockout protection in `DeleteCredential` only counts APPROVED credentials — a rejected/never-approved additional passkey must never block deletion of the sole real means of access.

**Device linking via code (`AuthController.LinkBegin`/`RegisterBeginLinked`):** an alternative to the browser-dependent WebAuthn cross-device/hybrid transport (QR code + Bluetooth), which depending on browser/OS/context may not be discoverable at all, or only behind a hidden "more options" link, and additionally requires the two devices to be physically nearby. An already-logged-in device generates, via `POST link/begin` (session-required), a short-lived 8-character code (Crockford Base32, `32^8` combinations, 10-minute validity, `IMemoryCache` instead of DB — the same category of transient state as the WebAuthn challenges). The NEW, not-yet-logged-in device opens the standalone route `/link` (`PublicLayout`, its own page `Link.razor`) and enters the code there; `POST register/begin-linked` is deliberately reachable WITHOUT a session requirement (the calling device has none) — the authorization sits in the code itself, which only an already-logged-in device could have issued. Each device registers its OWN local passkey (`navigator.credentials.create()` runs on the new device itself, no cross-device ceremony) and lands — like with `begin-additional` — as PENDING until the original device approves it via the device list; the code itself only proves "which account", not "this is genuinely trustworthy". One-way: after the first SUCCESSFUL `register/complete`, the code is removed from the cache (`PendingRegistration.LinkCode`); failed/aborted attempts before that leave it untouched (retry without a new code from device A). `PendingRegistration.RequiresSessionAtComplete` internally distinguishes whether `RegisterComplete`, with `ForAuthUserId` set, additionally requires a valid session (true = `begin-additional`) or not (false = `begin-linked`, where there is none).

**Tests (`PasskeyAuthTests`, `PasskeyTestHelpers`):** `FakePasskey` is a simulated authenticator with a real ECDSA-P256 key that builds standards-compliant attestation objects ("none" format, CBOR via `System.Formats.Cbor`) and assertion signatures — Fido2NetLib thus verifies the real crypto path in the tests, nothing is mocked.

## Per-user API key, Phase 3 (`SettingsController.cs` ha-api-key endpoints, migration `AddPerUserApiKey`)

Phase 3 replaces the last remnant of the single-user auth model: instead of ONE global, monthly-rotating API key (`ApiKeyProvider`, `app_data/api-key.json`, bootstrap endpoint, `X-Api-Key-Rotated` grace-window mechanism — all removed), every `AuthUserEntity` now optionally carries its **own, long-lived API key** (`ApiKeyHash` SHA-256 + `ApiKeyCreatedAt`, unique index on the hash).

- **Lifecycle:** `GET/POST /api/settings/ha-api-key[/generate|/revoke]` — all three require `[Authorize(Policy = "SessionOnly")]` (a real passkey session, not a bare API key), so a leaked key can't reissue itself or revoke someone else's key. Generate returns the plaintext exactly once (UI: `SetupHomeAssistantCard.razor` with a one-time display + copy button); regenerating overwrites the hash and immediately invalidates the old key; revoke sets it to null.
- **Why long-lived instead of rotating (an explicit user decision):** Home Assistant has no live session that could notice a rotation — the old 30-day rotation mechanism would have silently disabled the integration after more than 10 days offline. A leak is instead handled via immediate revocation + regeneration.
- **Resolution:** `StudyLifeAuthenticationHandler` resolves API-key requests directly to the owning user via the hash match, identically for all four slots (Home Assistant/studylife-ai/studylife-mcp/studylife-capture) — there is no "first user" fallback anywhere anymore (see the Phase-2 section above, audit finding A2).
- **Tests:** `PerUserApiKeyTests` (lifecycle, multi-user isolation across two keys, 404 for the removed bootstrap endpoint); `CustomWebApplicationFactory` seeds a fixed test key as a hash on the migrated test user for this and attaches it as an `X-Api-Key` default header to all test clients.

## Passkey recovery codes (`AuthController.7.Recovery.cs`, migration `AddRecoveryCodes`)

Emergency access when the only registered device/passkey is lost and no device link exists — without this, recovery would only be possible via direct DB intervention by the operator. Standard "one-time code" pattern (as with GitHub/Google): `POST /api/auth/recovery/generate` (session-required, same rationale as ha-api-key — a leaked API key must not be able to construct its own emergency access) deletes all of the user's existing codes and issues 8 fresh ones (`XXXX-XXXX-XXXX`, 12 characters from a 32-char alphabet without `0/O/1/I` so they're safely readable from paper), returning the plaintexts exactly once; only `RecoveryCodeEntity.CodeHash` (SHA-256, unique index) is persisted. `POST /api/auth/recovery/login` is deliberately unauthenticated (gate exception like `login/begin`) — the hash lookup identifies the user directly, uniformly answers 401 for both "unknown" and "already used" (no information leak), and is throttled via its own, stricter rate-limit partition in `Program.cs` (brute-forcing 12-character codes is otherwise the only remaining attack vector). `GET /api/auth/recovery/status` reports the unused-code count and creation date for the Setup card's "Emergency Codes" section (`PasskeyDeviceManager`), which shows a two-step confirmation before regenerating (old codes become invalid) and a one-time copyable display of the new set. `Login.razor` exposes a subtle "Sign in with recovery code" link next to the normal passkey flow, landing on `/setup` afterwards instead of `/` — the natural next step after an emergency login is registering a new passkey.

## Registration gate + invites (`Services/RegistrationGateService.cs`, `AuthController.2.Invites.cs`, migration `AddAuthInvites`)

Audit finding A10: open self-registration (`register/begin` with no `ForAuthUserId`, i.e. NOT `begin-additional`/`begin-linked`) is now gated by `Registration:Mode` (env `Registration__Mode`) — `open` (anyone may register, the previous unconditional behavior), `invite` (a valid, unused, unexpired invite token is required at `begin` and consumed at `complete`), or `closed` (nobody self-registers). **Unset or an unrecognized value defaults to `invite`** — the safer choice, so an instance that never configured this explicitly doesn't stay silently wide open.

**Bootstrap bypass, deliberately NOT keyed on "zero `AuthUsers`":** the gate is skipped entirely while `!PasskeyCredentials.AnyAsync()` — the exact same predicate the pre-existing setup-secret check in `RegisterBegin` already uses, and the one this app has always used for "the instance hasn't been claimed/set up yet" (see the Phase-2 section above). A textbook fresh install still carries the Phase-1 legacy `AuthUser` with zero passkeys at this point — `AuthUsers.Count() == 0` is only the rarer "restored an empty/wiped DB" edge case, a strict subset. Gating on `AuthUsers` count instead would brick every normal upgrade path: nobody could ever be logged in yet to generate the first invite (invite creation is owner-only), so `Registration:Mode=invite`'s default would permanently lock the very first registration on every fresh deployment. The setup-secret check itself is untouched by this feature and keeps applying during bootstrap exactly as before.

**Invites (`AuthInviteEntity`, owner-only via `AuthController.IsOwnerAsync()`/`Forbid()` — the same manual pattern as `BackupController`, deliberately NOT `[Authorize(Policy = "SessionOnly")]` so a non-owner session gets 403 not 401, and deliberately absent from `ApiKeyScopes` so a bare API key gets 403 via the scope-only-failure exception instead):** `POST /api/auth/invites` creates one and returns the plaintext token exactly once (only `TokenHash`, SHA-256, is stored — same convention as every other credential in this schema); `GET /api/auth/invites` lists id/created/expires/used state, never the token; `DELETE /api/auth/invites/{id}` revokes one. Default lifetime 7 days (`RegistrationGateService.InviteLifetime`). The shareable link is `{origin}/register?invite={token}` (`SetupInvitesCard.razor` builds it client-side); `Register.razor` reads `?invite=` from the URL and forwards it through both `begin` and `complete` unchanged.

**Consumption is atomic and happens at `complete`, never at `begin`:** `RegistrationGateService.TryConsumeInviteAsync` compiles to a single `UPDATE AuthInvites SET UsedAt=…, UsedByUserId=… WHERE TokenHash=@hash AND UsedAt IS NULL AND ExpiresAt > @now`, run inside `RegisterComplete`'s existing transaction. A failed/abandoned attestation attempt therefore never burns the invite (nothing between `begin` and a successful `complete` touches `UsedAt`), and two concurrent `complete` calls racing on the same token resolve cleanly — only one `UPDATE` can ever match, the loser gets `affected == 0`, rolls back its own transaction, and receives the same `invite_invalid` 403 as a never-valid token.

**Client-visible error shape:** a gated rejection (at either `begin` or `complete`) answers `403` with `RegistrationGateErrorDto { Reason }`, one of three stable strings — `"closed"`, `"invite_required"`, `"invite_invalid"` — so `Register.razor` can show a specific, localized message (`AuthText.RegisterClosed`/`RegisterInviteRequiredHint`/`RegisterInviteInvalid`) instead of the generic `RegisterFailed` text.

## Live Activity push (`Services/ApnsSender.cs`, `Services/BackgroundTaskService.LiveActivity.cs`, `Controllers/TimerStateController.cs`)

Keeps the native app's (`studylife-app` repo) iOS lock-screen/Dynamic-Island focus timer updating through phase transitions even while the app is fully terminated — the same "plug-in" pattern as the per-user API key: purely config-gated, no feature flag. `ApnsSender` stays fully inert (`Enabled=false`) as long as `Apns:KeyPath`/`Apns:KeyId`/`Apns:TeamId`/`Apns:BundleId` aren't all configured; `Apns:UseSandbox` switches between `api.sandbox.push.apple.com` (development-profile installs) and the production endpoint. `PUT /api/timerstate/liveactivity-token` (session-required) lets the app register/clear its current ActivityKit push token, stored on `TimerStateEntity`. The background worker's 5-second tick (`BackgroundTaskService.LiveActivity.cs`) sends an ActivityKit content-state update on every phase transition (focus↔break, round increment) and an `event: end` on completion — **critically, it only persists the new phase state (`IsBreak`/`CurrentRound`/`PhaseEndsAt`) after a successful or definitively-invalid-token APNs outcome**; a transient send failure (`ApnsSendOutcome.Failed`) returns early without saving, so the next tick retries the same transition instead of silently skipping it (a real bug found and fixed via live device testing — the lock screen briefly froze on the old phase for up to a minute after a transient APNs error). Content-state dates are encoded as Unix-epoch seconds via a custom `Codable` extension on the Swift side (`TimerActivityAttributes.ContentState`) — Swift's default `Date` `Codable` uses seconds since 2001-01-01, which ActivityKit's push-payload decoder does not expect.

## Planner (`Pages/Planner.razor`, `Shared/StudyPlanner.cs`, `Controllers/PlannerController.cs`)

- **Shared logic:** slot search (`FindFreeSlots`: daily window, study days, conflict avoidance,
  half-hour grid, 30-min buffer) and course weighting (`WeightedRoundRobin`, smooth weighted
  round-robin like nginx) live in `StudyLife.Shared.StudyPlanner` — used identically by the
  browser Planner (preview + confirm) and the server endpoint `POST /api/planner/exam-plan`
  (Home Assistant service `generate_exam_plan`, saves directly with no preview).
- **Course resolution now study-program-aware (since 2026-07-19):** the server endpoint resolves the course like
  `ProgressController`/`CoursesController` do — an active custom study program via
  `StudyProgramCatalog.LoadCoursesAsync`, otherwise the built-in catalog. Previously it only knew
  `CourseCatalog.AppliedAICourses`.
- **Weekly plan target:** uses the configurable `WeeklyGoalMin/MaxHours` from settings
  (same values as the dashboard quota/reports/HA); falls back to 25–30h if 0/inconsistent.
  The demand calculation (sessions needed from remaining hours) is deliberately implemented in parallel in the client and the
  controller — documented duplication analogous to the HA coordinator.
- **Tests:** `StudyPlannerTests` (Shared, slot/weighting logic including edge cases) and
  `PlannerControllerTests` (integration: built-in + custom course, validation, study window/
  study days). The Planner has counted toward the coverage target since the protective rule was lifted
  (`tools/coverage-report.py`).
