# Reproducible builds

What can be rebuilt bit for bit from this repository, how to check it, and where the current
gaps are.

## What makes the build repeatable

- **Pinned inputs.** NuGet restores run in locked mode against the committed
  `packages.lock.json` files (`Directory.Build.props`, `RestoreLockedMode` on CI). GitHub
  Actions are pinned by commit SHA, and the Docker base images by digest
  (`src/StudyLife.Server/Dockerfile`).
- **Deterministic compiler output.** `Deterministic=true` is the .NET SDK default, so there are
  no timestamps or random GUIDs in assemblies. On CI (`CI=true`) `Directory.Build.props` also
  sets `ContinuousIntegrationBuild=true`, which maps source paths in PDBs and assemblies to
  `/_/` so the output does not depend on the checkout directory.
- **Deterministic source generators.** The typed text classes of Toolbelt.Blazor.I18nText are
  generated by `src/StudyLife.I18nTextGenerator` instead of the package's own generator (see
  [the client assembly](#the-client-assembly-fixed-2026-11-03) below).
- **A fixed timestamp.** When `SOURCE_DATE_EPOCH` is set (the
  [reproducible-builds.org](https://reproducible-builds.org/docs/source-date-epoch/)
  convention), every static web asset gets that time as its `Last-Modified` header in
  `StudyLife.Server.staticwebassets.endpoints.json` instead of the file's modification time
  (`src/StudyLife.Server/StudyLife.Server.csproj`). The release job and the reproducibility
  check set it to the commit time: `SOURCE_DATE_EPOCH=$(git log -1 --format=%ct)`.
- **Same command everywhere.** The release asset `server.zip` is the zipped output of
  ```sh
  SOURCE_DATE_EPOCH=$(git log -1 --format=%ct) \
  dotnet publish src/StudyLife.Server/StudyLife.Server.csproj --configuration Release \
    --runtime linux-x64 --no-self-contained -p:Version=<version> --output publish/amd64
  ```
  run on `ubuntu-latest` with the .NET SDK from `DOTNET_VERSION` in
  `.github/workflows/ci-cd.yml`. The container images copy exactly that output.

## Checking it

`.github/workflows/reproducibility.yml` publishes the server twice from clean trees of the
same commit and compares all ~1700 output files with SHA-256 (`scripts/compare_builds.py`). It
runs weekly, on demand, and on PRs that touch build inputs. **Every file must be identical**;
there are no known exceptions, so any difference fails the run. Between the two builds the
workflow also stops the compiler and MSBuild servers (`dotnet build-server shutdown`), so the
second build starts as cold as the first.

To check by hand, run the publish command above twice with `CI=true` (or
`-p:ContinuousIntegrationBuild=true`) and the same `SOURCE_DATE_EPOCH`, running
`dotnet build-server shutdown` and `git clean -xdf` in between, and then:

```sh
python3 scripts/compare_builds.py <output-1> <output-2>
```

To compare against a release, build the release tag (`git checkout v<version>`) with
`-p:Version=<version>` and `SOURCE_DATE_EPOCH` set to that tag's commit time, and compare with
the unpacked `server.zip` of that GitHub Release (compare the unpacked files: the zip archive
itself records file times). Before you compare, verify the download as described in
[SECURITY.md](../SECURITY.md#verifying-releases).

## The client assembly (fixed 2026-11-03)

Until 2026-11-03, two clean publishes of the same commit gave 1685 of 1703 files bit-identical:
`StudyLife.Client.dll`/`.pdb` differed, and with them everything that records the client's
hash (the fingerprinted `wwwroot/_framework/StudyLife.Client.<hash>.wasm*` files, `dotnet.js*`,
`service-worker*.js`, the static web asset manifest).

**Root cause.** Toolbelt.Blazor.I18nText 14.1.1's source generator compiles the 17 text tables
in a `Parallel.ForEach` over a `ConcurrentDictionary` and passes the results to
`AddSource` from a `ConcurrentBag`, so the generated classes reached the compilation in
thread-completion order. Their content was identical every time, but the order is visible in
the assembly: the type table (`StudyLife.Client.I18nText.*` came out in a different sequence on
every build), the user-string heap that follows method order, and the PDB document table.
The PDB ID and the MVID are hashes over all of that, so the whole file changed. A
metadata-level comparison of two builds showed exactly this and nothing else: the same 720
types, 5556 methods and 2533 strings, in a different order. Declaring the classes in a fixed
order by hand fixed the type table but not the PDB, whose document order follows the order of
the generated sources.

**Fix.** `src/StudyLife.I18nTextGenerator` is a small source generator that calls the
package's own `I18nTextCompiler` (same options, same code, same hint names) and adds the
results sorted by hint name. `StudyLife.Client.csproj` hides `I18nTextUseSourceGenerator` from
the compiler, which switches the package's generator off, and references the replacement
instead. The generated code is unchanged. The build fails with `SLI18N002` if the
Toolbelt.Blazor.I18nText runtime package and the generator package it wraps ever differ in
version; Dependabot bumps both in one PR (`i18ntext` group in `.github/dependabot.yml`).
After changing the generator project locally, run `dotnet build-server shutdown` so a running
compiler server does not keep the previous build loaded.

The second source of differences was `StudyLife.Server.staticwebassets.endpoints.json`: its
`Last-Modified` headers came from file modification times, which are the build time for every
generated or compressed asset. `SOURCE_DATE_EPOCH` (above) replaces them.

Result: **1700 of 1700 files bit-identical** for two clean builds in the same directory.

## Known gaps

- **Different checkout directory.** A build from another directory still differs in
  `StudyLife.Client.dll`/`.pdb` (and the files carrying its hash). The Razor source generator
  writes the absolute path of each `.razor` file into the generated C# (`#pragma checksum`,
  `#line`), so the generated text and its hash in the PDB depend on the directory. Path
  mapping does not reach text inside generated sources, and the Razor compiler has no option
  to emit relative paths. Every other file, including the server, Shared, Tts and Stt
  assemblies, is identical across directories. To reproduce a release exactly, build in the
  same directory GitHub Actions uses: `/home/runner/work/studylife/studylife` (for example in
  a container with the repository mounted there).
- **Container images** are not bit-reproducible yet. The `apt-get` layer (espeak-ng, curl)
  installs whatever the Debian mirror serves on build day, and layer timestamps are not
  normalised (`SOURCE_DATE_EPOCH` is not passed to the Docker build). The downloaded voice and
  model files are already fixed: they come from commit-pinned Hugging Face URLs and are checked
  with `sha256sum -c` in the Dockerfile. The image provenance (SLSA, `mode=max`) records the
  exact inputs of every published image, which makes an image auditable even though it cannot
  be rebuilt bit for bit.

## Next steps

1. Pass `SOURCE_DATE_EPOCH` to the Docker build and pin the Debian packages through a snapshot
   mirror.
2. Drop `src/StudyLife.I18nTextGenerator` once Toolbelt.Blazor.I18nText adds its sources in a
   deterministic order upstream.
